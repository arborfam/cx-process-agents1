# Журнал рішень

Формат: ID · статус · рішення · причина · наслідок / ціна · альтернатива · коли й як переглянути.

Статуси: **Запропоновано** (чекає погодження власниці) · **Погоджено** · **Відхилено** · **Замінено**. Змінювати статус може лише власниця продукту (або за її явною вказівкою). Повний контекст — docs/technical-plan.md.

Станом на 30.09.2026: **погоджено власницею** — Node.js + TypeScript (D1) і SQLite (D3) для зрізу 1; **D21** (непідтримуваний елемент BPMN → пояснення, AS-IS лишається погодженим); **D26** (основний результат `.bpmn`, `.drawio` — експорт); **D27** (явний початковий крок); **D28** (некритичні прогалини можуть лишатися в погодженому AS-IS, невизначеність потоку блокує BPMN); **D29** (роль агента 2: модель — смислова перевірка, інструменти запускає код); **D30** (ліцензії; водяний знак bpmn.io лишається); **D31** (відхилення зауваження агента 2 з поясненням без обходу кодових перевірок); **D32** (збій моделі зупиняє другий етап із повтором; режиму «без смислової перевірки» у v1 немає); **D33** (порядок блоків картки); **D34** (перевірки потоку: початковий крок, досяжність, вихід до завершення; старі записи — явне уточнення); з **D22** — збереження оригіналів і перенесення логіки на TypeScript на етапі зрізу 3. **Станом на 01.10.2026 додатково погоджено власницею D61 і D62 (з уточненнями; реалізовано як підготовчий крок до 3b) і підтверджено виправлення D60.** Усі інші рішення лишаються **запропонованими**, навіть ті, що вже реалізовані у зрізі 1 (реалізація не є погодженням).

## D1 · Погоджено для зрізу 1 (29.09.2026, повідомлення власниці) · Один застосунок Node.js + TypeScript
- **Рішення:** сервер, правила, запуск агентів і перевірка BPMN — в одному проєкті на TypeScript.
- **Причина:** Node 22 є в середовищі; екосистема BPMN (bpmn-js, bpmn-moddle) найсильніша в JavaScript; схеми даних описуються один раз для API та перевірки відповідей моделі.
- **Ціна:** якщо підтримувати продукт будуть Python-фахівці, доведеться навчатися TypeScript.
- **Альтернатива:** Python + FastAPI (див. technical-plan §1).
- **Перегляд:** до початку зрізу 1.

## D2 · Запропоновано · Браузер — лише показ і введення; рішення приймає сервер
- **Причина:** інваріант CLAUDE.md — блокування BPMN у програмній логіці, а не в кнопці.
- **Наслідок:** кожна дія перевіряється на сервері незалежно від інтерфейсу.
- **Перевірка:** тест прямого запиту до backend без погодження (зріз 1).

## D3 · Погоджено для зрізу 1 (29.09.2026, повідомлення власниці) · Кейси зберігаються у файлі SQLite
- **Причина:** один файл, без окремого сервера БД, легко копіювати й видаляти; достатньо для одного користувача.
- **Ціна:** не підходить для багатьох одночасних користувачів.
- **Альтернатива:** Postgres — лише при багатокористувацькому хмарному розміщенні.
- **Перегляд:** якщо з’явиться потреба в спільній роботі кількох людей.

## D4 · Запропоновано (уточнено 29.09.2026) · Моделі викликаються лише з сервера; BPMN будує код із погодженого пакета, а перевірка порівнює готовий файл із пакетом
- **Рішення:** зміст схеми (дії, ролі, умови, переходи) береться з погодженої версії AS-IS **дослівно**; агент 2 не переписує кроки, а лише перевіряє однозначність і повертає питання із посиланнями на ID кроків. XML будує код. Технічні елементи (початок, кінець, ексклюзивний шлюз, лінії, доріжки) — за жорстким переліком; таймери, повідомлення, підпроцеси, паралельні шлюзи заборонені, доки їх немає в описі.
- **Причина уточнення:** генерація кодом сама по собі не гарантує правильності змісту; технічні елементи можуть непомітно додати бізнес-поведінку.
- **Перевірка:** код зворотним розбором відновлює граф із файлу й звіряє з погодженим пакетом: дії, ролі, умови, переходи, технічні елементи, повноту, версію (technical-plan §1а). Негативні приклади (додана задача, підмінена умова, не та доріжка, втрачений цикл, зайвий таймер, застаріла версія) мають бути відхилені.
- **Межа гарантії:** перевірка доводить, що схема нічого не додає і не втрачає відносно опису; правильність самого опису лишається за аналітиком; людське приймання за таблицею «крок ↔ елемент» обов’язкове.
- **Наявний пайплайн власниці та зворотна перевірка:** див. D22–D23 і docs/bpmn-pipeline-assessment.md.
- **Непідтримувані елементи (уточнено 29.09.2026, див. D21, погоджено):** якщо процес потребує елемента поза дозволеним переліком, система повертає пояснення обмеження, а не змінює логіку процесу.
- **Ціна:** потрібен власний генератор, розбір і розкладка; якість автоматичної розкладки не перевірена.
- **Перевірка рішення:** зріз 3a на вручну підготованому пакеті.

## D5 · Запропоновано (реалізовано у зрізі 1; погодження стосувалося SQLite, а не конкретного драйвера) · Вбудований `node:sqlite` із тонким шаром доступу до даних
- **Причина:** немає нативної збірки; працює в Node 22 (перевірено в цій сесії).
- **Ризик:** Node позначає модуль як експериментальний.
- **Запобіжник:** усе спілкування з базою — через один модуль; заміна на `better-sqlite3` — невелика зміна.
- **Перегляд:** на зрізі 1, якщо з’являться нестабільність або попередження, що заважають.

## D6 · Запропоновано · Розміщення: спочатку локальний запуск; хостинг — лише за окремим рішенням
- **Причина:** cloud-сесія Claude Code — середовище розробки, тимчасове; інтерв’ю можуть бути конфіденційними; CLAUDE.md забороняє публікувати кейси без дозволу.
- **Варіант А (за замовчуванням):** запуск на комп’ютері власниці. **Варіант Б:** захищений хостинг із паролем — потребує явної згоди, бо дані потрапляють на сторонній сервер.
- **Потрібне від власниці:** вибір до кінця зрізу 2. Для зрізу 1 не потрібно.
- **Статус доступу:** нічого не опубліковано, хостинг не обрано.

## D7 · Запропоновано · Застосунок має власний API-ключ моделі; доступ Claude Code його не замінює
- **Причина:** Claude Code — засіб розробки; runtime-виклики продукту — окремий доступ з окремою оплатою.
- **Факт середовища:** `ANTHROPIC_API_KEY` не задано (перевірено 29.09.2026, значення не друкувались). Тому **справжні AI-виклики зараз недоступні.**
- **Правила:** ключ — лише змінна середовища/секрет; `.env` у `.gitignore`; ліміт витрат у консолі постачальника до першого запуску.
- **Потрібне від власниці:** створити ключ і ліміт перед зрізом 2; підтвердити, чи обираємо Anthropic API.
- **Не перевірено:** чи покриває ваша поточна підписка API-доступ.

## D8 · Запропоновано · Модель — параметр конфігурації, не «зашитий» вибір
- **Порядок:** обидва агенти спершу на моделі середнього класу; порівняти з потужнішою на двох контрольних кейсах; лишити найдешевшу, що проходить перевірки.
- **Причина:** вартість і якість невідомі до вимірювання (спец. §9, §11).
- **Не робити:** називати ціни чи ліміти з пам’яті — звірити з офіційною сторінкою перед запуском.

## D9 · Запропоновано · Деморежим і справжній режим розділені явною змінною; мовчазного переходу немає
- **Рішення:** `MODEL_MODE=demo|real`; у `demo` — постійна помітка «ДЕМОРЕЖИМ — не AI» на екрані, у версії, у журналі й у експортованому документі; у `real` без ключа застосунок не стартує.
- **Причина:** CLAUDE.md забороняє підміняти доступ до моделі демонстраційними відповідями без явної позначки.
- **Наслідок:** версія, створена в деморежимі, лишається позначеною назавжди.
- **Перевірка:** тест «real без ключа → помилка старту»; тест наявності позначки у версії та експорті.

## D10 · Запропоновано · Незмінні записи: змінення = нова версія
- **Рішення:** `source`, зміст `as_is_version`, `approval`, `audit_log` не оновлюються й не видаляються; це забезпечено і кодом, і тригерами SQLite.
- **Причина:** інваріанти «оновлення не знищує правки, історію та прийняті версії» й «погодження прив’язане до незмінної версії».
- **Тип твердження** (`source_fact` / `analyst_confirmed` / `hypothesis` / `improvement_proposal` / `unknown`) зберігається на кожному твердженні, щоб не втрачати походження.
- **Ціна:** база зростає; потрібне явне «замінена» замість видалення.

## D11 · Запропоновано · Стани кейсу за специфікацією; запуск агента — окремий технічний стан
- **Рішення:** Дослідження → На погодженні → AS-IS погоджено → BPMN на перевірці → Завершено; будь-яке нове джерело чи зміна змісту повертає до «Дослідження» й позначає погодження `superseded` (без видалення).
- **Прийняття робочої версії ≠ погодження AS-IS.**
- **Причина:** спец. §2. Помилка лише у схемі не змінює AS-IS: створюється новий артефакт.

## D12 · Запропоновано · Серверна перевірка `canStartBpmn` у транзакції; вхід агента 2 береться з бази за ID погодження
- **7 умов:** стан; чинне погодження людини; збіг хеша; версія найновіша; немає нових джерел; немає відкритих критичних питань; немає активного запуску.
- **Агент не має доступу до модуля погодження й не має інструментів із побічними діями; вбудовані у джерела команди — дані.**
- **Застарілі результати:** агент 1 — зберігається як пропозиція на застарілій основі; агент 2 — стан `stale`.
- **Обмеження, яке слід пам’ятати:** прототип однокористувацький; захист від помилок агента й обходу кнопки, а не від людини з доступом до бази.

## D13 · Запропоновано · Перший зріз підтримує вставлений текст, `.txt`, `.md`
- **Причина:** мінімум ризику помилок читання. `.docx`/`.pdf` — після перших реальних кейсів.
- **Наслідок:** непрочитаний файл має статус `error`, не вважається опрацьованим і блокує погодження.

## D14 · Запропоновано · Помилки не знищують прийняті версії й не просувають стан
- **Правила:** одна автоматична повторна спроба лише для тимчасових збоїв; змістову прогалину повторним запуском не «лікуємо»; без нескінченних циклів. Таблиця — technical-plan §8.
- **Числові ліміти** (час, обсяг, вартість, кількість запусків) — початкові припущення; фіксуються після вимірювання на зрізі 2.

## D15 · Запропоновано (оновлено 29.09.2026; порядок блоків змінено рішенням D33) · Структура картки
- **Перший екран:** шапка (назва, версія, текстовий статус, режим) · суть · **головні зміни як коротка змістовна різниця** («було … → стало …», без голих назв полів) · **окремий блок «Критичні прогалини»** (питання, невизначені переходи, суперечності) · **окремий блок «Статус перевірки чернетки»** з підписами Пройдено/Не пройдено/Увага · одна наступна дія із поясненням блокування.
- **Деталі й докази** — окремо; біля твердження — тип і перехід до точного фрагмента джерела; невизначений перехід у кроках виділено й пов’язано з питанням.
- **Причина:** CLAUDE.md, спец. §3; виправлення суперечності «Q1 каже невідомо, а крок S5 стверджував END».
- **Перевірка:** тести огляду змін і блоків (зріз 1); оцінка людиною «за хвилину» — зріз 4.

## D16 · Запропоновано · Чотири зрізи зі зупинкою після кожного
1. Каркас довіри без AI (збереження, версії, погодження, серверне блокування). 2. Справжній агент 1. 3. BPMN (3a без AI, 3b агент 2). 4. Наскрізні кейси й підсумковий документ.
- **Причина:** найдорожчі й найризикованіші частини (модель, BPMN) не починаються, доки не доведені правила.
- **Кількість агентів:** рівно два продуктові. Технічні перевірки — код. Семантичну перевірку цитат відкладено до доказаної потреби.

## D17 · Запропоновано · Hooks: жодного не активовано; кандидати з’являться після зрізу 1a
- **Причина:** docs/hooks-plan.md забороняє команди-пустишки; реальні команди (`npm test`, `npm run typecheck`) ще не існують.
- **Кандидати:** SessionStart (`npm ci`), PostToolUse для `prompts/**` і схем, CI на push; PreToolUse для теки очікувань — лише за окремою згодою.
- **Умова активації:** перевірка події, успішного випадку, відомого дефекту, тайм-ауту, відсутньої залежності й фактичного завантаження в новій cloud-сесії.

## D18 · Запропоновано (29.09.2026, за уточненням власниці) · Політика даних: справжній запуск передає обрані матеріали провайдеру моделі
- **Факт:** навіть при локальному запуску застосунку текст джерел, обраних для аналізу, передається до API провайдера. Локально лишається лише база кейсів.
- **Рішення:** для навчальних і контрольних перевірок — лише синтетичні матеріали. Реальні матеріали до провайдера не передаються без окремого рішення власниці й прочитаних умов провайдера (не перевірено).
- **Запобіжник (для зрізу 2):** позначка походження джерела `synthetic`/`real`/`demo_script`; справжній запуск відмовляється брати `real`, доки для кейсу людина не ввімкнула згоду (запис у журналі).
- **Зріз 1:** поле `origin` є, форма за замовчуванням ставить «синтетичний»; запусків моделі немає, тож нічого не передається.
- **Зв’язок із D6:** розміщення лишається відкритим; хостинг (варіант Б) додає ще одного одержувача даних.

## D19 · Запропоновано (реалізовано у зрізі 1) · Технічні рішення зрізу 1
- **Сервер без фреймворку:** стандартний `http` Node + невеликий роутер; залежності лише `zod` (схеми) у роботі; `tsx`, `typescript`, `playwright-core` — для розробки й знімків. Причина: менше рухомих частин для навчального прототипу.
- **Сесія людини:** код доступу (`data/access-code.txt`, створюється при першому запуску, поза git) → cookie `HttpOnly`, `SameSite=Strict`. Сервер слухає лише `127.0.0.1`. Код агентів не має доступу до сесії й до модуля погодження. Це не повноцінна автентифікація: прототип однокористувацький.
- **Права:** усі дії, що змінюють стан, потребують актора-людини; погодження додатково вимагає підтвердження списку перевірки.
- **Правки аналітика (власність):** що аналітик ввів або змінив, позначається «власним»; агент не може це перезаписати — зберігається варіант аналітика, обидва показуються як конфлікт. Наслідок: усе, що аналітик вводить із нуля, вважається його власним, тому агент, змінюючи такий елемент, породжує конфлікт, а не мовчазну правку.
- **Форма редагування:** кроки й проблеми — прості рядки `ID | … | …` (аналітикиня не пише JSON); ID кроків стабільні.
- **Деморежим:** демо-кейс і його питання задані сценарієм (`origin=demo_script`) і так позначені; «Оновити аналіз (AI)» вимкнена. Агент 1 у зрізі 1 представлений лише підставним клієнтом для тестів логіки запусків (mode=demo, недоступний з інтерфейсу).
- **Запуск BPMN у зрізі 1:** сервер перевіряє дозвіл і записує запуск зі станом `not_implemented`; побудови схеми немає (зріз 3).
- **Версія Node.js:** мінімум 22.13 (`engines` + `.npmrc engine-strict`, старіша версія зупиняє `npm install` з чіткою причиною). Перевірено фактично: 22.12.0 — `node:sqlite` недоступний; 22.13.0, 22.22.2 і 24.21.0 — типізація й усі тести проходять.
- **Перегляд:** після відгуку власниці на зріз 1.

## D35–D44 · **Запропоновано / реалізовано в зрізі 2** (01.10.2026; на час реалізації модель, бюджет і ключ **не були погоджені** — пізніше погоджено, див. D63; успішних викликів не було)
- **D35 Підключення моделі.** Лише з сервера, офіційний SDK `@anthropic-ai/sdk` (MIT). Автоповтори SDK вимкнено: єдину повторну спробу контролює застосунок. Структурований вивід за схемою змісту (`output_config.format`); `thinking`, `temperature`, примусовий `tool_choice` не передаються (Opus 5.5 їх не приймає/не потребує). Відповіді `refusal` і `max_tokens` — явна помилка, неповна відповідь не приймається.
- **D36 Режим real.** Стартує лише з повним набором: ключ, `CX_MODEL` (явно, без значення за замовчуванням), `CX_BUDGET_USD_TOTAL`; інакше застосунок відмовляє зі списком, чого бракує, і **не** переходить на деморежим. Ціни — `config/model-pricing.json` (дата перевірки, джерело); модель без ціни не запускається. *Правило змінено явно:* тест зрізу 1 «real завжди відмовляє» замінено на «real без повної конфігурації відмовляє» (причина: real тепер реалізовано).
- **D37 Ліміти.** До кожного виклику (і до повтору): обсяг входу (`CX_MAX_INPUT_CHARS`, 150 000), запусків на кейс (12) і на добу (20), найгірша оцінка вартості проти ліміту на запуск ($1.5) і проти залишку загального бюджету; оцінка входу з запасом (1.8 симв./токен). Відмови не створюють запусків і записуються в журнал. Максимум 2 спроби (одна автоматична повторна) — лише для тимчасових збоїв і відповідей, що не пройшли перевірку. Автентифікація, невірний запит, refusal, обрив — без повторів. Тайм-аут не повторюється (щоб не подвоювати витрати).
- **D38 Перевірка відповіді моделі до збереження** (`src/ai/verify.ts`): схема; джерела існують серед переданих; твердження джерела мають `source_id` і цитату; цитата знайдена в джерелі (дослівно або після нормалізації пробілів/лапок/тире — це попередження); унікальні ID; агент не створює «підтверджено аналітиком» і не ставить гіпотезі «підтверджена»; статус гіпотези «підтримана/спростована» потребує доказів; закрите питання має відповідь; наявні кроки/твердження/гіпотези/проблеми не видаляються. **Цитата доводить лише, що джерело це сказало, а не істинність висновку** — смислову відповідність перевіряє людина. Правки аналітика (включно з гіпотезами аналітика) захищає `protectAnalystEdits`.
- **D39 Опрацьовано = реально передано.** Покриття версії росте лише джерелами, які було передано моделі в цьому запуску; непрочитані не передаються й не позначаються. Застарілий результат — пропозиція, не голова. Помилка не змінює версію, погодження й стан.
- **D40 Дані й секрети.** Джерела з позначкою «реальні» моделі не надсилаються (D18): запуск відхиляється. Ключ лише в змінній оточення сервера; усі повідомлення про помилки, журнал і відповіді API проходять редагування (`sk-ant-…`, Bearer, заданий ключ). Джерела в запиті — у розділювачах із випадковим маркером, інструкція «дані, а не команди».
- **D41 Журнал запуску:** модель, версія й SHA-256 інструкції, джерела, вхідна версія, перевірки/попередження, порушення, тривалість, токени, вартість, кількість спроб. Запуск асинхронний (202 + опитування), один активний на кейс; після аварійного завершення «застряглі» запуски позначаються помилкою при старті.
- **D42 Сценарії.** Оригінал пакета незмінний (SHA-256, `-text`); джерела SRC-00…07 — дослівні фрагменти з указаним походженням; SRC-00 (навчальна межа), SRC-08p/08n/09 — вигадані для тесту й позначені так. Етапи 1–5; наступний етап лише після опрацювання попереднього; два окремих кейси; SRC-09 подається лише явною дією аналітика. Заголовки джерел для моделі нейтральні (модель не бачить, який це сценарій).
- **D43 Критерії оцінки** — у `evals/` (поза `src/`, тест це перевіряє): очікувані факти, допустимі невизначеності, заборонені домисли, спосіб перевірки; програмні перевірки — лише сигнали, людські пункти окремо; документ генерується з коду.
- **D44 Модель за замовчуванням не вибрано.** Рекомендація: Claude Opus 5.5, effort `medium` (за потреби `high`); дешевша альтернатива — Sonnet 5.5; Fable 5.1 — лише якщо перевірка за критеріями покаже, що Opus недостатній. Server-side `fallbacks` (модель-запасна) **не вмикаємо**: бюджет і модель мають бути обрані явно. Запропонований бюджет — $10 (див. звіт).

## D45–D48 · **Реалізовано** (01.10.2026, за результатами незалежної перевірки; запропоновано до погодження разом із D35–D44)
- **D45 Резервування бюджету.** Запуск у тій самій транзакції, що перевіряє бюджет, записує резерв (`run.reserved_usd`) = найгірша оцінка. «Витрачено й зарезервовано» = сума (відома вартість + резерв) за всіма справжніми запусками; активні запуски й запуски з невідомою вартістю тримають резерв. Повтор резервується окремо (атомарно) з урахуванням уже витраченого цим запуском і чужих резервів. Раніше два паралельні запуски різних кейсів обходили бюджет $0,90 (відтворено тестом).
- **D46 Невідома вартість.** Якщо usage невідомий (тайм-аут, обрив, мережа, 5xx, перезапуск під час запуску), `cost_usd = NULL`, `cost_known = 0`, а консервативний резерв (відоме + найгірша оцінка невідомої спроби) лишається в `reserved_usd` назавжди (переживає перезапуск; звільнити його може лише людина після звірки з Console — цієї дії поки немає). Помилки до генерації (4xx) — вартість відома й нульова. Оцінка входу (1,8 симв./токен із запасом 25 %) враховує інструкцію, повідомлення **і схему відповіді**; вона **не є гарантованою межею** — фактичний usage перекриває її; жорстка межа лише для виходу (`max_tokens`).
- **D47 Цитати.** Частини цитати зі скороченням «…» перевіряються всі, незалежно від довжини, в тому самому порядку; збіг зі скороченням — окремий вид `elided` (попередження: пропущене між частинами перевіряє людина). Приклад із перевірки («НЕ БУЛО … Повідомлення опубліковано.») тепер «не знайдено».
- **D48 Вилучення/заміна кроку.** Агент не прибирає кроків (DELETED_ITEMS лишається), а додає `step_proposals`: дія, крок, (крок-заміна), причина, джерело + дослівна цитата-доказ, статус `proposed`. Рішення — лише людина (`decideStepProposal`): прийняття створює нову версію (старі лишаються), переходи на вилучений крок перенаправляються на заміну або стають «невідомо» з критичним питанням, початковий крок переноситься/знімається, погодження втрачає чинність, кроки стають «власністю» аналітикині. Відкрита пропозиція — критична прогалина (блокує погодження). Захист правок аналітика не змінено; агент не може змінити/прибрати наявну пропозицію чи повернути вилучений крок. Інструкція агента → v0.3.

## D49–D59 · **Запропоновано / реалізовано в зрізі 3a** (01.10.2026; без викликів моделі; жодне з цих рішень ще не погоджено власницею)

- **D49 Вхід і прив'язка до версії.** Єдиний вхід генератора — «погоджений пакет»: ID версії, SHA-256 її змісту, зміст AS-IS, назва пулу, позначка походження (`product` / `test-fixture`). Назва пулу — назва кейсу; вона **не входить у зміст AS-IS і не покрита хешем версії** (це відома межа). **[Замінено D62, 01.10.2026: тепер напис на пулі = `process_name` зі змісту версії, під хешем і погодженням; назва кейсу в схему не потрапляє.]** Тестові пакети позначені «створено без AI» у файлі, `.drawio`, переглядачі й індексі.

ID кроку для генератора: літери/цифри/`_`/`-`, з літери (як у доменному шарі), `END` і `UNKNOWN` зарезервовані. - **D51 Тексти.** Дії, ролі, умови, тригер, назва пулу переносяться **дослівно**. Лапки, апострофи, `& < >`, «ялинки», кирилиця, емодзі, перенос рядка, розмітко-подібні послідовності (`<b>`) — **коректний вхід, зберігається без втрат** (в оригіналі лапки мовчки губили текст). Відхиляються: керівні символи, **табуляція і повернення каретки** (лейаутер записує табуляцію «сирою», XML-розбір за стандартом перетворює її на пробіл — тиха втрата; тест це доводить), `[TO DEFINE …]`. - **D52 Переходи й K1.** Крок із ≥2 переходами → безіменний ексклюзивний шлюз; умови — підписи ліній. **Кілька різних умов в одну ціль — коректно** (унікальні ID ліній; дві лінії, що збігалися б, розводяться біля цілі). Блокують (K1): єдина умовна гілка без «інакше»; порожня умова при розгалуженні; та сама умова в різні цілі; повтор того самого переходу; перехід «невідомо»; відкрите критичне питання; відкрита пропозиція вилучення кроку; кроки без входу/виходу, замкнений цикл без виходу; відсутній чи хибний початок. **Некритичне (K2) не блокує**: відкриті некритичні питання, гіпотези, оцінки, конфлікти, роль без кроків (доріжка створюється порожньою), — лишаються в переліку «відомі обмеження» поруч зі схемою.
- **D53 Статуси результату.** `ok` (файл видано) · `blocked` (K1 або некоректний вхід: пояснення, файлу немає) · `unsupported` (D21: пояснення за зразком плану — які кроки, який елемент, що без відображення, що погодження не змінено, варіанти; файлу немає) · `verification_failed` (зворотна перевірка або лейаутер відхилили результат: файл **не видається**). Якщо є і K1, і непідтримувана нотація — `blocked` із обома списками. **Обмеження:** у змісті AS-IS немає структурних позначок «паралельно/таймер/…», тож у 3a їх задають лише тестові пакети (`unsupported_marks`); автоматично їх наближено виявлятиме агент 2 (3b). Додати структурне поле до схеми AS-IS — окреме рішення власниці (змінює зміст і хеш версій). **[Виконано D61, 01.10.2026: поле `notation_requirements` у змісті версії; окремого входу `unsupported_marks` більше немає.]**
- **D54 Розкладка.** `bpmn-auto-layout@2.0.0-alpha.2` (версія прибита, MIT), виклик як бібліотеки, у пам'яті. Лейаутер **ігнорує розміри з входу** і малює задачі 100×80, тож довгий підпис виповзав би з блока; після розкладки схема пропорційно збільшується (задачі — разом зі схемою; події, шлюзи й підписи не змінюють розміру) за найдовшою дією, ширини 100…260 px. Підписи умов лишаються на тій самій відстані від своєї лінії (+8 px запасу). **Будь-яке попередження лейаутера блокує видачу** (відомий код `DI_NOT_CREATED` = елемент без геометрії). Оцінка ширини тексту калібрована вимірюванням у Chromium: для Arial/Liberation завищена ≈15 %, для запасного DejaVu збігається; **виміряно на Linux, не на Windows**.
- **D55 Геометрія.** Помилки (файл не видається): відсутня/нечислова/нульова геометрія елемента чи лінії, накладання блоків, блок поза доріжкою, доріжка поза пулом, стрілка, не прикріплена до своїх блоків, надто коротка стрілка, **лінії, що повністю збігаються (одну не видно)**, назва, що явно не вміщується в блок. Попередження (показуються, не блокують): стрілка проходить крізь чужий блок, підпис накладається на блок чи інший підпис, підпис може не вміститися в рамку. Для всіх тестових пакетів — нуль попереджень.
- **D56 `.drawio`.** Експорт із перевіреного `.bpmn`: ID клітинок = ID елементів (ID кроків збережено), лінії проходять через ті самі проміжні точки й виходять/входять у ті самі точки блоків, підпис початкової події переноситься (від'ємні відступи), підписи умов стоять у позиції, обраній лейаутером. Власна звірка за пакетом і за `.bpmn`: підписи, ролі, переходи (за самим `.drawio`), ID, кількість стрілок, геометрія, зайва нотація (маркери, символи, тип шлюзу). Провал звірки **не скасовує чинний `.bpmn`**: експорт позначається невдалим і не видається. Вигляд перевірено в офіційному переглядачі draw.io (`viewer-static`, завантажений лише в тимчасову теку для знімків, у репозиторій не додається); **у десктопному/онлайн-застосунку draw.io не відкривалось**.

Обхід обов'язкової смислової перевірки не створено; у 3b продуктовий шлях вимагатиме завершеної перевірки агента 2. Генератор не має доступу до запису в базу: `unsupported`/`blocked` не змінюють ні версію, ні погодження (тест знімає стан бази до й після).

## D61 · **Погоджено** (01.10.2026, власниця, з уточненнями) · **Реалізовано** як підготовчий крок до 3b · Явні вимоги до нотації (паралельність, таймер…) зберігаються у версії AS-IS

  - вимоги зберігаються **у змісті версії** (`notation_requirements`), отже **під хешем і людським погодженням**;
  - порожнє або відсутнє поле означає **«не зазначено»**, а не «особливостей немає»;
  - **агент 1 пропонує** вимогу з дослівною цитатою, **людина підтверджує** чи відхиляє; непідтверджена пропозиція не стає встановленим фактом;
  - **агент 2** може запропонувати додаткову знахідку, але **не змінює погоджений пакет** (запис у `prompts/bpmn.md`; реалізація — у 3b);
  - **підтверджена** непідтримувана вимога дає `unsupported` **без виклику моделі**: файл не створюється, погодження AS-IS лишається чинним (D21);
  - для підтримуваних випадків смислова перевірка агента 2 **залишається обов'язковою**; окремої обов'язкової відмітки «нотацію перевірено» **не додано**.

  - *Людина* (`src/domain.ts`): додає вимогу (одразу `confirmed`, нова версія), підтверджує/відхиляє пропозицію, прибирає вимогу (стара версія лишається в історії); перевірки вводу — вид, пояснення, існуючий крок, дублікат «крок + вид», джерело кейсу. Лише для людини (`FORBIDDEN` для агента); HTTP: `notation/add|decide|remove` за сесією й заголовком захисту.
  - *Агент 1* (`src/ai/verify.ts`, `prompts/analyst.md` v0.4): лише `proposed` без рішення й підпису, обов'язкові джерело й цитата, що є в джерелі; крок існує; пояснення непорожнє; без дублікатів; повторна пропозиція без нового доказу після відхилення — порушення. `protectAnalystEdits`: наявні вимоги агент не змінює й не видаляє (відновлюється, пишеться конфлікт), нові нормалізуються до «пропозиція агента».
  - *Блокування:* пропозиція без рішення — критична прогалина: блокує передачу на погодження, погодження й серверний дозвіл BPMN (захист у глибину) і генерацію; вимога до неіснуючого кроку — так само. ## D72 · **Запропоновано** (01.10.2026, вимоги записані до початку робіт) · Вимоги до майбутнього редизайну інтерфейсу: універсальність для різних процесів
- **Головна вимога: інтерфейс універсальний для різних процесів аналітика.** CX — **тестовий кейс**, а не предметна область продукту: його ролі (CX, овнер, агенти підтримки, відповідальна за підготовку), терміни (handover, FAQ, база знань, запуск) і етапи сценарію **не зашиваються** в структуру продукту — ні в схему, ні в назви полів і вкладок, ні в тексти інтерфейсу, ні в правила перевірок. Усе предметне лишається в **даних кейсу**, у сценарії (`scenarios/`) і в критеріях (`evals/`).
- **Зберегти:** вкладки (аналітикиня вже звикла до цієї навігації) і початок опису з **бізнес-контексту** — навіщо процес, хто отримує результат, яка проблема, які межі відомі.
- **Розділити три різні за природою речі** (зараз вони змішані в одному списку прогалин):
  - **бізнес-прогалини** — чого ми ще не знаємо про процес (відкриті питання, невідомі переходи, непідтверджена послідовність, «причину не з'ясовано»);
  - **рішення аналітика** — що чекає її вибору (пропозиції кроків, вимоги до нотації, початковий крок, межі, конфлікти з правками);
  - **технічні помилки** — що неправильно в самому опису або в запуску (структурні порушення, збої моделі, відхилені спроби, непідтримувана нотація).
- **Навчальні кнопки етапів** сценарію (перехід до наступного етапу, явне уточнення) **відокремити** від звичайних дій роботи з матеріалами — додавання інтерв'ю, документів і уточнень: зараз навчальний сценарій і звичайна робота виглядають однаково, і це вчить неправильному.
- **Перевірка дизайну — на двох процесах:** на CX і **на іншому процесі** (інша предметна область, інші ролі, інші терміни). Якщо для другого процесу доводиться щось перейменовувати в продукті — вимога універсальності не виконана.
- **Межі:** редизайн у цій задачі **не починався**; жодного рішення про макет не прийнято. Чинні блокування, погодження на хеші, незмінність версій і серверні перевірки редизайн не послаблює.

- **Що сталося.** Прогін analyst-v0.7 обірвався: 51 801 вх. / 48 000 вих. токенів, 341,2 с, $1,167, поточна версія не змінилась. Раніше таке саме обрізання було на стелі 32 000.
- **Доведено арифметикою — це була ОДНА спроба.** Opus 5.5 коштує $4/$20 за млн: 51 801 × 4/10⁶ + 48 000 × 20/10⁶ = **$1,1672** — рівно стільки й списано. Обрив через `max_tokens` не є повторюваним збоєм (`ModelFailure.retryable` не містить `truncated`), тож повтору не було. Вихід став рівно на `CX_MAX_OUTPUT_TOKENS`, `stop_reason: max_tokens`, неповна відповідь не прийнята — усі перевірки відпрацювали правильно.
- **Виміряно (на експорті контрольного прогону v0.5, етап 2).** Інструкція 13 281 симв.; AS-IS із відступами `JSON.stringify(…, null, 1)` 39 841, компактно 35 060 — **4 781 симв. чистих відступів**; JSON-схема в тілі (режим `text_json`) 6 137; джерела 4 623. Калібровка на двох справжніх прогонах: етап 1 — 2 спроби × 21 739 симв. → 16 133 вх. токени; етап 2 — 37 610 симв. → 14 970. Обидва дають **≈ 2,5 символа на токен** для цього змісту. Отже 51 801 вх. токенів ≈ 130 000 символів промпта: накопичений AS-IS виріс приблизно до 65 000 символів.
- **Дублювання є, але здебільшого потрібне.** 3 416 символів цитат у твердженнях дослівно повторюють текст джерел, які надсилаються повністю; уточнення йдуть і як джерела `clarification`, і як `questions[].answer`. Прибрати не можна: цитата і є доказом, а дослівність перевіряє програма. Це **не** основна причина обсягу.
- **Справжня причина — структурна.** Інструкція вимагає «повна оновлена версія змісту (разом із незмінним, що було раніше)», а п. 11 забороняє видаляти. Відповідь не може бути меншою за весь накопичений AS-IS і зростає з кожним етапом: етап 2 дав 35 060 символів відповіді ≈ 14 000 токенів.
- **Міркування й відповідь ділять одну стелю.** В Opus 5.5 міркування **не можна вимкнути**, вони завжди генеруються й оплачуються (навіть коли текст прихований), входять в `output_tokens`, а `max_tokens` — жорстка межа, **про яку модель не знає**. Виміряно один раз (етап 2): 25 836 вихідних токенів при відповіді ≈ 14 000 ⇒ **≈ 0,84 токена міркувань на токен відповіді**.
- **Межа доказів.** Розділити 48 000 вихідних токенів на міркування й відповідь **постфактум неможливо**: окремого лічильника токенів міркувань API не повертає, а `display` у нас «omitted». Тому «відповідь мала б ≈ 26 000, міркування ≈ 22 000» — припущення з калібровки, не вимір. Так само невідомо, чи завершився б прогін із більшою стелею.
- **Рішення 1 — прибрано марну вагу входу (без втрати змісту).** AS-IS надсилається **компактним** JSON (відступи нічого не пояснюють моделі); з вигляду для моделі прибрано поля, якими володіє програма і які вона все одно перезаписує: `conflicts` (їх формує `protectAnalystEdits`) і `questions[].link_history` (її веде застосунок, `verify.ts` завжди відновлює з попередньої версії). Надсилати їх і вимагати назад — подвійна вага, що зростає з кожною версією (конфлікти можуть містити повні тексти «збережено/запропоновано»). На стані етапу 2 це **−4 781 символ ≈ 1 900 токенів, 7,4 % промпта**; на більшому стані економія зростає пропорційно. Інструкція — **analyst-v0.8**: `conflicts` повертати як `[]`, `link_history` не створювати; решту повертати **повністю**, нічого не скорочувати заради меншої відповіді.
- **Рішення 2 — зупинка ДО оплати замість оплаченого обриву.** `answerFeasibility` оцінює, чи вміститься відповідь: накопичений зміст — нижня межа відповіді (`contentChars / 2,5 × 1,25` запасу), плюс міркування (`× 2,0`, виміряно 0,84 із запасом). Якщо не вміщується, `beginAnalystRun` для справжнього клієнта зупиняє запуск (`OUTPUT_TOO_LARGE`, HTTP 413) **до виклику моделі**: запуску не створено, витрат немає, версія не змінена, відмова в журналі. Пояснення називає числа й змістовні дії (менші етапи, закрити з'ясовані питання уточненнями, прийняти пропозиції), а підняття `CX_MAX_OUTPUT_TOKENS` згадує **останнім** із прямим застереженням, що наступний етап упреться в ту саму межу.
- **Калібровка перевірена на фактах:** прогін, який справді завершився (етап 2, 35 060 симв.), перевірку **проходить** (потрібно ≈ 35 060 при стелі 48 000); обірваний (≈ 65 000 симв.) — **зупиняється** (потрібно ≈ 65 000). Тобто жоден успішний прогін новою перевіркою не блокується.
- **Рішення 3 — зростання видно.** У журналі запуску (`checks_json.size`) записуються `content_chars`, `prompt_chars` і `answer_tokens`; `checks_json` тепер доповнюється, а не перезаписується при завершенні.
- **Чого свідомо НЕ зроблено.** Не піднято `max_tokens` (це лікує симптом: наступний етап упреться знову). Не прибрано джерела, докази, історію чи питання заради меншої відповіді. Не змінено `effort` — це погоджений параметр (D63) і рішення власниці. Не додано кешування запиту: стабільна частина (інструкція ≈ 4 000 токенів) мала порівняно з мінливою (увесь AS-IS), тож виграш був би малий.
- **Структурна межа лишається (окреме рішення, див. D79).** Поки контракт «повертай увесь зміст щоразу» чинний, опис рано чи пізно переросте будь-яку стелю. Зменшити відповідь без втрати даних можна лише зміною протоколу.
- **Перевірено.** Цільові `tests/request-size.test.ts` — **11/11** (компактний JSON, відсутність програмних полів, збереження всього змістовного, оцінка вміщення, зупинка до оплати з числами й без поради «просто підніми ліміт», контроль що звичайний кейс проходить, що деморежим не обмежується, що розмір видно в журналі, і що захист правок аналітикині не послаблено). Повний набір `npm test` — **682/682**, 0 пропущено (було 671/671); `npx tsc --noEmit` — чисто. Платних викликів не робили, бюджет і ліміти не піднімали, користувацьку `data` не змінювали.

## D79 · **Запропоновано** (02.10.2026; не реалізовувати без рішення власниці) · Протокол оновлення AS-IS: повна відповідь щоразу не масштабується
- **Проблема.** Агент зобов'язаний повертати **весь** накопичений AS-IS у кожній відповіді. Розмір відповіді дорівнює розміру опису й зростає з кожним етапом: 11 177 символів після етапу 1 → 35 060 після етапу 2 → ≈ 65 000 на момент обриву. Разом із міркуваннями (їх в Opus 5.5 не вимкнути) це впирається в будь-яку стелю: спершу 32 000, потім 48 000.
- **Чому це не лікується збільшенням ліміту.** Кожне підняття дає один-два етапи й коштує дедалі дорожче: вихід оплачується за найвищою ставкою ($20 за млн), а переписування незмінного тексту — чиста переплата. На обірваному прогоні 96 % вартості ($0,96 з $1,167) — це вихід.
- **Варіанти (жоден не реалізовано).**
  1. **Часткове оновлення.** Агент повертає лише **нове й змінене** (додані твердження, питання, кроки; змінені за ID), програма зливає з попередньою версією. Відповідь перестає залежати від накопиченого обсягу. Ціна: новий контракт відповіді, нова перевірка злиття, нові способи обійти захист (видалення через «не згадав») — потрібні окремі блокування й тести. Найбільший виграш, найбільший ризик.
  2. **Менші етапи.** Менше нових джерел за прогін; зміст росте повільніше. Нічого не змінює в коді, але лише відсуває межу.
  3. **Розділення опису.** Один кейс — одна ділянка процесу; великі процеси описуються кількома кейсами. Змінює продуктову модель, а не лише запит.
- **Що вже зроблено й не потребує рішення (D78):** прибрано марну вагу входу, додано зупинку до оплати з числами, зростання видно в журналі.
- **Рекомендація:** варіант 2 як негайний обхід для наскрізного прогону; варіант 1 планувати окремо — разом із редизайном (D72), бо він змінює і контракт агента, і те, що бачить аналітикиня.
