# Звіт: підготовчий крок до 3b — D61 (вимоги до нотації) і D62 (назва процесу) (01.10.2026)

> **Період дії.** Історичний звіт підготовки до зрізу 3b (01.10.2026). Поточний стан — `README.md` і `docs/handoff.md`.

**Головне:** обидва погоджені рішення реалізовано у змісті версії, редагуванні, перевірках, генераторі й інтерфейсі; старі версії, їхні хеші та погодження не переписано. **Жодного виклику моделі, платного нічого, ключ не запитувався.** Агент 2, зріз 3b та інші можливості поза цими двома рішеннями не додавались. Дані користувача (`data/`), оригінали пайплайна й наявні кейси не змінювались.

## 1. Що змінилось для користувача
| Було | Стало |
|---|---|
| Напис на пулі схеми = назва кейсу, поза хешем і погодженням | Напис на пулі = **назва процесу** (`process_name`) у змісті версії: під хешем і погодженням; зміна = нова версія. Назва кейсу лишається міткою у списку й у схему **не потрапляє** |
| Непідтримувану нотацію можна було задати лише у тестовому пакеті | **Вимоги до нотації** (`notation_requirements`) — частина змісту версії. Людина додає (одразу підтверджена) або підтверджує/відхиляє пропозицію агента 1 (з цитатою). Підтверджена вимога → `unsupported` без моделі, погодження AS-IS чинне |
| Порожнє поле — неоднозначне | Порожнє чи відсутнє = **«не зазначено»**, а не «особливостей немає»; смислова перевірка агента 2 для підтримуваних випадків залишається обов'язковою; окремої галочки «нотацію перевірено» немає |
| Старий запис без назви | Версія й погодження **не змінюються**; дозвіл BPMN з'являється після явного уточнення (нова версія → прийняття → погодження); наступна дія — «Уточнити назву процесу»; назву кейсу не підставлено |

Видимість: назва процесу — у «Суті», на вкладці «Бізнес-контекст і межі», у формі редагування та в **діалозі погодження** (разом із вимогами до нотації); вимоги — з перевіреною цитатою й кнопками «Підтвердити / Відхилити / Прибрати»; пропозиція без рішення — критична прогалина й пункт перевірки готовності. Знімки: `docs/demo/22–26` (проходження у браузері, `scripts/walkthrough-notation.ts`; «пропозицію агента» створено програмно, не AI).

## 2. Як це влаштовано (простими словами)
- **Єдине джерело правди.** Генератор схем бере і назву пулу, і непідтримувані вимоги **лише зі змісту погодженої версії**. Окремого входу «позначки» чи «назви пулу» більше немає, тож нічого не можна підсунути повз хеш і погодження.
- **Агент пропонує, людина вирішує.** Перевірка відповіді агента 1 вимагає: статус лише «пропозиція», без підпису людини, пояснення, існуючий крок, джерело й **дослівну цитату, що є в тексті**; повтор відхиленої без нового доказу — помилка. Якщо все ж щось пройде, `protectAnalystEdits` не дасть агентові змінити/видалити/підтвердити наявну вимогу чи змінити назву процесу: відновлює й записує конфлікт.
- **Непідтверджене не стає фактом, але й не губиться.** Пропозиція без рішення блокує передачу на погодження, погодження, серверний дозвіл BPMN і генерацію, доки людина не вирішить.
- **Старі дані недоторкані.** Поля необов'язкові; для старого змісту JSON і хеш **ідентичні** тим, що давав код до змін (золотий хеш, обчислений старою схемою). Збереження старого запису через форму (яка завжди надсилає порожню назву) нових полів у нього не створює.

## 3. Що фактично перевірено
- `npm test`: **398 із 398** (було 371; +27: 21 у `tests/notation-process-name.test.ts`, 6 нових у `bpmn-input`/`bpmn-version`), 0 пропущено. `tsc --noEmit` чистий. Наявні тести адаптовано лише там, де змінилась форма даних (назва процесу тепер у змісті; інструкція v0.4; «погоджений запис без назви» не отримує дозволу BPMN) — жоден тест не послаблено.
- **Старі версії й погодження:** золотий хеш; правка без нових полів і правка через форму не додають їх; старий погоджений запис — версія й погодження побайтово не змінились після перевірок, явне уточнення створює нову версію, погодження старої скасовано (лишилось в історії), дозвіл — лише після нового погодження.
- **Назва процесу:** під хешем; нова версія при зміні; те саме значення — без нової версії; обрізання пробілів і межа довжини; явне зняття; назва кейсу ніколи не потрапляє у зміст, пакет чи результат; видимість у картці, редакторі, діалозі погодження.
- **Вимоги:** додавання, дублікат, неправильний вид/крок/джерело, лише людина; підтвердження/відхилення/повтор рішення; прибрання з історією; наскрізно з запуском агента: пропозиція з цитатою зберігається як `proposed`, блокує, підтверджена людиною → `unsupported` без моделі, погодження й версії побайтово не змінились.
- **Захист від агента:** вигадана цитата, відсутній доказ, хибний крок, «підтверджено» агентом, підпис іменем людини, дублікати, повтор відхиленого, зміна/видалення підтвердженої вимоги, зміна назви процесу — відхилено чи відновлено з записом конфлікту.
- **Без обходів:** пропозиція чи вимога до неіснуючого кроку блокує передачу, погодження (кейс примусово «На погодженні») і дозвіл (погодження записано напряму); API: без сесії — 401, без заголовка захисту — 403, застаріла основа — 409; маршрути рішень виконуються лише від імені людини; генератор відмовляє без назви навіть для пакета, складеного повз домен.
- **Мутаційна перевірка:** 17 навмисних поломок нових правил (агент змінює назву/вимогу, підтверджує, без цитати; дозвіл і генерація без назви; підтверджена вимога ігнорується; пропозиція не блокує; підстановка назви; поле з'являється в старому записі; рішення двічі; дублікат; вимога без кроку; рішення від агента через API) — усі виявлені; одну (`T12`) спершу не виявлено — прогалина в тестах (форма завжди надсилає порожню назву) — додано тест, виявлено. Повторно проведена мутаційна перевірка попередніх правил 3a: 15 із 16 (шістнадцята — відомий еквівалентний випадок вимкнення дублюючої гілки; його чесну версію виявлено).
- **Браузер:** `scripts/walkthrough-notation.ts` — назва видима в «Суті», описі, діалозі погодження; підтвердження пропозиції створює нову версію; додавання вимоги вручну; уточнення назви в старому записі; назву кейсу не підставлено.

## 4. Що не працює / не перевірено
- **Схема відповіді моделі зросла:** ≈4,8 → ≈5,7 КБ, необов'язкових властивостей 3 → 5, union-типів немає. Чи API її прийме, **перевірити неможливо без виклику** (як і раніше; запасний режим `CX_OUTPUT_MODE=text_json`). Модель може не виявити вимог або надумати їх — цитату перевіряє програма, істинність — людина; якість такого виявлення не вимірювалась (моделі не було).
- Агент 2, його смислова перевірка й знахідки `UNSUPPORTED_CANDIDATE` — **не реалізовані** (3b): у `prompts/bpmn.md` лише зафіксовано межі (агент не змінює пакет, не знімає вимог).
- Windows, шрифти Windows, застосунок draw.io — як і раніше не перевірялись.
- Назва процесу перевіряється лише на допустимі символи й довжину; один пул; учасники/кілька пулів — окреме рішення.
- Погоджені раніше записи потребуватимуть назви перед побудовою схеми (це наслідок D62, а не помилка).
