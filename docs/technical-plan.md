## 1. Рекомендований мінімальний варіант (D1–D4)

**Один невеликий застосунок на Node.js + TypeScript**, який складається з трьох частин у одному проєкті й одному запуску:

```
 БРАУЗЕР (аналітикиня)          СЕРВЕР (один процес)                 ЗОВНІШНЄ
 ┌──────────────────┐   HTTP    ┌────────────────────────────┐
 │ Прості сторінки: │ ────────► │ 1. API                     │
 │ список кейсів,   │           │ 2. Правила (стани,         │      ┌──────────────┐
 │ картка, джерела, │ ◄──────── │    погодження, блокування) │ ───► │ API моделі   │
 │ питання, версії, │           │ 3. Запуск агентів          │      │ (потрібен    │
 │ переглядач BPMN  │           │ 4. Генерація й перевірка   │      │  окремий     │
 └──────────────────┘           │    BPMN                    │      │  ключ, D7)   │
                                └────────────┬───────────────┘      └──────────────┘
                                             ▼
                                   Файл бази SQLite (кейси)
```

### Що де працює

| Питання | Рішення | Пояснення |
|---|---|---|
| Що працює в браузері | Лише показ і введення: сторінки без важкого фреймворку; переглядач/редактор BPMN (бібліотека bpmn-js) | Браузер **нічого не вирішує**: кнопка «Створити BPMN» — лише зручність, не захист |
| Де зберігаються кейси | Файл SQLite на сервері застосунку (одна база, вся історія) | Один файл легко копіювати, резервувати, видаляти. Без окремого сервера БД |
| Де викликаються моделі | **Лише на сервері.** Браузер ніколи не бачить ключа і не звертається до моделі | Ключ не потрапляє до репозиторію і до сторінки; сервер може перевірити дозвіл до виклику |
| Як формується BPMN | **Зміст схеми (дії, ролі, умови, переходи) береться з погодженого пакета AS-IS дослівно.** Агент 2 не переписує кроки: він лише перевіряє однозначність і повертає питання та посилання на ID кроків. **BPMN-XML будує наш генератор на TypeScript** (за логікою вашого Python-ланцюга, але з перевірками входу), **розкладку виконує `bpmn-auto-layout`** (npm, версія прибита), експорт у `.drawio` — окремий крок (розділ 1б) | Модель не може змінити текст дії, роль чи умову переходу: вони копіюються з погодженої версії. Технічні елементи додає код за жорстким переліком дозволених типів — розділи 1а і 1б |
| Як перевіряється BPMN | Код **зворотним розбором** файлу відновлює з нього граф і порівнює з погодженим пакетом: дії, ролі, умови, переходи (розділ 1а). Далі — людина звіряє схему з описом за таблицею «крок ↔ елемент» | Технічна коректність ≠ змістова правильність (спец. §8). Це прямо показується в інтерфейсі |
| Мова та інструменти | TypeScript; `zod` для схем даних; `node:test`/`tsx` для тестів; bpmn-moddle і bpmn-auto-layout для BPMN | Одна мова для сервера й перевірок; схеми один раз описані й використовуються і для API, і для перевірки відповіді моделі |

### Суттєві альтернативи (лише там, де змінюють вартість/складність)

- **Python + FastAPI замість Node.** Python простіший для сервера, але екосистема перевірки й показу BPMN сильніша в JavaScript. Обрав би Python лише якщо командою підтримки будуть Python-розробники.
- **Готовий конструктор (no-code/низько-код) замість власного коду.** Швидше для інтерфейсу, але серверний контроль погодження й незмінні версії там або неможливі, або прив’язують до платформи. Не рекомендується, бо це ядро продукту.
- **Postgres замість SQLite.** Потрібен лише при кількох одночасних користувачах або хмарному розміщенні з масштабуванням. Для прототипу — зайва вартість.

## 1а. Перевірка відповідності BPMN погодженому AS-IS (уточнення 1; D4)

**Проблема.** Те, що BPMN створено кодом, не гарантує правильності змісту: код може помилитися у зіставленні, а технічні елементи (шлюзи, події) можуть непомітно додати бізнес-поведінку. Тому перевірка порівнює **готовий файл** із **погодженим пакетом**, а не довіряє генератору.

**Принцип.** Код розбирає створений `.bpmn` назад у граф («зворотний розбір») і звіряє його з погодженою версією. Усе, чого немає в погодженому пакеті, — відхилення.

| Що перевіряється | Правило | Приклад порушення, який має бути виявлений |
|---|---|---|
| **Дії** | Кожен погоджений крок → рівно один елемент-задача з його ID; назва задачі збігається з дією кроку **дослівно**. Задач без ID кроку немає | Додано задачу «Повідомити керівника»; змінено формулювання дії |
| **Ролі** | На кожну погоджену роль — одна доріжка (lane); задача лежить у доріжці ролі свого кроку. Доріжок без погодженої ролі немає | Крок S3 потрапив у доріжку чужої ролі; з’явилася нова роль «Система» |
| **Умови** | Кожен виходячий із розгалуження перехід має підпис, що збігається з умовою в описі кроку **дослівно**; кількість виходів = кількості переходів кроку | Умову «погоджено» замінено на «так»; втрачено гілку «відхилено» |
| **Переходи** | Множина ребер «крок → крок / кінець», отримана з BPMN після згортання технічних елементів, **точно дорівнює** множині переходів погодженого опису, включно з поверненнями (цикли) | Втрачено повернення S2 → S1; з’явився перехід S4 → S2, якого немає в описі |
| **Технічні елементи** | Дозволені лише: початкова подія (без типу), кінцева подія (без типу), ексклюзивний шлюз, лінія потоку, процес/учасник, доріжки. Шлюз може існувати лише там, де крок має кілька переходів з умовами. Таймери, повідомлення, підпроцеси, гранична подія, паралельні шлюзи, артефакти даних — **заборонені**, поки їх немає в погодженому описі | Додано таймер очікування «1 день»; додано паралельний шлюз |
| **Тексти технічних елементів** | Назви й документація технічних елементів порожні або складаються лише з тексту умов/кроків погодженого опису | У документації шлюзу з’явилося «вважається завершеним через 5 днів» |
| **Повнота й зв’язність** | Кожен елемент досяжний від початку; кожен шлях завершується кінцевою подією; зайвих кроків немає; усі погоджені кроки відображені | Крок S5 без вхідної лінії; шлях без завершення |
| **Прив’язка версії** | У файлі записано ID і хеш погодженої версії; перевірка відхиляє файл, побудований на іншій версії | Схема створена на попередній версії |

**Що з неоднозначністю.** Якщо крок має кілька переходів, а з опису не видно, чи вони взаємовиключні (умови можуть виконуватися одночасно), це **неоднозначність**: агент 2 повертає питання, схема не будується (спец. §8). Код не вгадує «паралельність» чи «ексклюзивність».

**Як доводимо, що перевірка працює.** Набір негативних прикладів: кожне порушення з таблиці (додана задача, підмінена умова, не та доріжка, втрачений цикл, зайвий таймер, застаріла версія) створюється навмисно й **має бути відхилене**. Тест, у якому порушення не виявлене, вважається провалом перевірки, а не провалом прикладу. Це входить у критерії зрізу 3a.

### Якщо процес потребує непідтримуваного елемента (уточнення 3; D21 — **погоджено власницею 29.09.2026**)

Перша версія генератора підтримує лише елементи з таблиці вище. Якщо погоджений AS-IS потребує чогось поза цим переліком — паралельних гілок, таймера («через 3 дні автоматично»), повідомлень між учасниками, підпроцесу, граничної події, артефактів даних — **система не спрощує процес і не підбирає «найближчий» елемент**. Вона зупиняє побудову й повертає **пояснення обмеження**.

| Що робить система | Чого система не робить |
|---|---|
| Створює запис `unsupported` з поясненням: які кроки (ID) і який тип елемента потрібен; чому його не підтримано у цій версії; що саме залишилося без відображення; які є варіанти для аналітика (залишити як текстову примітку до кроку, попросити розширити підтримку, свідомо спростити опис і погодити нову версію) | Не замінює таймер звичайною задачею, паралельні гілки — послідовністю, повідомлення — лінією потоку |
| Не створює `.bpmn`-файлу, поки хоч одна вимога не відображається точно. Часткової схеми «з пропусками» не видає | Не змінює погоджений AS-IS і не скасовує погодження: опис не помилковий, обмежений інструмент |
| Показує обмеження в підсумковому документі та в інтерфейсі | Не позначає кейс «Завершено» |

**Як виявляється.** (1) Точно — за структурними позначками в погодженому пакеті, коли вони з’являться у схемі даних (наприклад, тип переходу «паралельно» чи «очікування»). (2) Наближено — агент 2 читає дії кроків і позначає ті, що описують непідтримувану поведінку; це семантична перевірка й **не гарантована**, тому людське приймання схеми лишається обов’язковим.

**Стан кейсу (погоджено).** AS-IS лишається погодженим, погодження не скасовується; побудова BPMN зупиняється з поясненням причини, артефакт має стан `unsupported`, а рішення (текстова примітка чи розширення підтримки) приймає аналітик. Специфікація §2 цього випадку не описувала, тож це рішення її доповнює.

**Критерії для зрізу 3a.** Приклад погодженого пакета зі кроком «паралельно» і кроком-таймером: результат — `unsupported` із назвою кроків; `.bpmn` не створено; хеш погодженої версії й погодження не змінилися; пояснення не містить «наближеної» схеми. Тест, у якому система тихо спростила процес, вважається провалом.

**Межа гарантії.** Ця перевірка доводить: схема **не додає і не втрачає** нічого відносно погодженого опису. Вона не доводить, що сам опис правильно відображає реальний процес — це відповідальність аналітика (спец. §4, §8). Тому людське приймання схеми за таблицею «крок ↔ елемент» лишається обов’язковим, а в інтерфейсі є явне попередження.

### Агент 2 отримує тільки погоджену версію і зберігає її зміст (D23)

Чотири незалежні бар'єри, кожен перевіряється тестом:

1. **Вхід.** Сервер завантажує пакет із бази **за ID погодження** (розділ 6). Агент 2 і генератор не приймають зміст із запиту, з джерел чи з сирих інтерв'ю. Пакет — це зміст погодженої версії (контекст, межі, ролі, кроки, переходи), незмінний, із хешем.
2. **Вихід агента.** Агент 2 повертає лише **питання й посилання на ID кроків** (наприклад, «кроки S3–S5: умови можуть виконуватися одночасно чи взаємовиключні?») та список непідтримуваних елементів. Поля з текстом дій, ролей чи умов у його відповіді **не приймаються** схемою (як strict-схема агента 1).
3. **Генератор.** Дії, ролі й умови **копіюються** з пакета, не переписуються й не «виправляються» (жодних замін ком, лапок чи регістру). Значення екрануються за правилами XML, а не видаляються.
4. **Зворотна перевірка** готового файлу (розділ 1а) — обов'язкова. Артефакт отримує статус `technical_ok` **лише якщо перевірка чиста**; інакше — `generation_failed` із зрозумілим поясненням (що саме відрізняється від пакета), і файл користувачеві **не видається**.

Ще: у записі артефакту фіксуються ID і хеш погодженої версії та ID погодження, версія генератора й лейаутера. Змінити пакет після запуску неможливо (розділи 4–6).

### Вимоги до погодженого пакета, які виявила інтеграція

- **Явний початковий крок (D27, погоджено).** Схема AS-IS нині не має поля «з якого кроку починається процес»; пробний адаптер оцінки припустив «перший у списку», і **це припущення відкинуто**: початковий крок задається лише явним полем `entry_step_id`, а порядок рядків не має жодного змісту. Визначення й правила — розділ 5б.
- **Єдина умовна гілка** («якщо X — крок Y», а інакше не сказано) — неоднозначність: агент 2 повертає питання, схему не будує.
- **Кілька умов у той самий крок** — дозволені (генератор створює унікальні ID переходів).
- **Не показуються на схемі** поля «результат», «умова входу», «вхідний артефакт» кроку: вони лишаються в погодженому описі й у таблиці «крок ↔ елемент». Це обмеження показується явно.
- **Тип виконавця** (людина/система/ручна) у схемі AS-IS відсутній: усі кроки — нейтральні задачі, без іконки «людина».
- **Кінцеві події** — без назв (їх текст у схемі AS-IS не задано окремо).

### Ізоляція запусків (D22)
Жодних фіксованих шляхів. Генерація й розкладка — **у пам'яті**; якщо файл потрібен, то в унікальній теці запуску (`mkdtemp`, права лише власника), яка видаляється після запуску. Модуль генератора не має глобального стану; вихід залежить лише від пакета. Тест: N паралельних запусків з різними пакетами (не менш як 20 пар) → кожен результат збігається зі своїм пакетом.

### Відхилення зауваження агента 2 (D31 — **погоджено власницею 30.09.2026**)

Аналітик може відхилити зауваження агента 2 **з поясненням**; рішення зберігається в історії. **Програмні перевірки цілісності та невизначеного потоку при цьому обійти не можна.**

| Питання | Правило |
|---|---|
| Хто | Лише людина-аналітик; агент і система — ні |
| Що можна відхилити | Лише знахідки класу `blocks_flow`, створені агентом 2 (смислова думка моделі) |
| Пояснення | Обов’язкове й непорожнє; без нього відхилення не записується |
| Як зберігається | Незмінний запис `finding_resolution`: копія знахідки (код, кроки, цитата, питання), рішення «відхилено», пояснення, хто, коли, ID запуску, ID погодження й хеш пакета. Видно на картці артефакту, в історії, у підсумковому документі («зауваження агента 2 відхилено: …») |
| Що не змінюється | AS-IS (нової версії немає), чинність погодження |
| Повторний запуск на тому самому пакеті | Попередні відхилення показуються як контекст, але потребують нового рішення |

**Чого відхилення не обходить** (код перевіряє це знову під час продовження і не залежить від рішень людини щодо знахідок):
1. серверний дозвіл `canStartBpmn` (чинне погодження, збіг хеша, найновіша версія, немає нових джерел…);
2. перевірка цілісності версії й хеша;
3. структурні прогалини потоку (K1): невизначені переходи, відсутній чи хибний початковий крок, недосяжні кроки, глухі кути, переходи на неіснуючі кроки, `[TO DEFINE]` (D27, D28);
4. непідтримувані елементи: `UNSUPPORTED_CANDIDATE` відхилити **неможливо** (D21);
5. зворотна перевірка `.bpmn` і звірка `.drawio`.

**Порядок.** Якщо є знахідки `blocks_flow`, запуск зупиняється в стані `awaiting_analyst`. По кожній знахідці аналітик обирає: (а) **уточнити AS-IS** — код створює нову версію з питаннями, кейс → «Дослідження», погодження скасовується з причиною `bpmn_ambiguity`, запуск закривається як `needs_clarification`; (б) **відхилити з поясненням**. Коли всі знахідки відхилено, «Продовжити» заново виконує кодові кроки 1–4 і 8–11 для того самого пакета (виклик моделі не повторюється). Якщо хоч одну знахідку вирішено через (а), відхилення в цьому запуску лишаються в історії, але нова версія потребує нового погодження й нового запуску.

**Межа гарантії.** Відхилення хибної знахідки може пропустити реальну неоднозначність: код не перевіряє смислу. Тому пояснення обов’язкове й видиме в підсумковому документі, а людська звірка схеми за таблицею «крок ↔ елемент» лишається.

### Інструменти: усе — код, модель жодного не викликає сама (v1; D29 — погоджено)
Оркестратор (код) запускає послідовно: `canStartBpmn` → `load_package` → `check_structure` → `scan_unsupported` → [виклик моделі] → `validate_findings` → [за потреби рішення аналітика щодо знахідок, D31] → `build_bpmn` → `verify_bpmn` → `export_drawio` + `verify_export` → `store_artifact`. **Модель отримує пакет і звіти кодових перевірок у контексті й повертає лише знахідки.** Вона не має доступу до файлів, оболонки, мережі, бази чи стану кейсу, не може змінювати пакет, погоджувати, змінювати статуси й запускати генерацію.
Причина: так найпростіше довести, що файли й перевірки — код, а результат відтворюваний. Якщо на зрізі 3b виявиться, що моделі корисно самій запитувати кодові перевірки, це буде окреме рішення з вузьким списком інструментів лише для читання.

### Збої моделі й деморежим (D32 — **погоджено власницею 30.09.2026**)
- **Недоступність моделі зупиняє другий етап; запуск можна повторити.** Якщо модель недоступна, тайм-аут або відповідь не за схемою (після однієї автоматичної повторної спроби для тимчасового збою, розділ 3): запуск отримує стан `error` на кроці смислової перевірки, артефакт **не створюється**, часткового результату немає, стан кейсу «AS-IS погоджено» і погодження **не змінюються**. Аналітик бачить причину й може **повторити запуск** — це новий запис запуску з посиланням `retry_of`; автоматичних циклів немає, кожен повтор фіксується в журналі.
- **Режиму «продовжити без смислової перевірки» у v1 немає.** Кодові кроки генерації не виконуються без завершеної смислової перевірки (тест: у продуктовому шляху немає гілки, що створює артефакт без неї). Повернення такого режиму — лише окремим рішенням власниці.
- **Деморежим:** агент 2 не імітується (D9). У продуктовому шляху другий етап зупиняється на смисловій перевірці з повідомленням, що потрібна модель, недоступна в деморежимі. Кодові компоненти (кроки 1–4 і 8–11) перевіряються у зрізі 3a **автоматичними тестами на підготованих пакетах**, а не продуктовою кнопкою. Показ вам результату 3a **погоджено** (30.09.2026): тестові пакети, згенеровані `.bpmn`/`.drawio` як файли й знімки переглядача, без окремої кнопки обходу в продукті.
- Ліміти: один виклик моделі на запуск (вхід — лише пакет і звіти), тайм-аут і одна автоматична повторна спроба (розділ 3), змістові прогалини повторним запуском не «лікуються».

## 3. Доступ до моделі для застосунку (D7)

Чи покриває вашу наявну підписку API-доступ — треба перевірити в вашому акаунті; я цього не припускаю.

Запропонований порядок: обидва агенти спершу на моделі середнього класу; на двох контрольних кейсах порівняти з потужнішою моделлю; лишити дешевшу, що проходить перевірки. Ціни й ліміти перевірити на офіційній сторінці перед стартом — я їх не наводжу з пам’яті.

### 3а. Політика даних під час запуску із зовнішнім API (уточнення 2; D18)

- **Локальний запуск не означає, що дані лишаються на комп'ютері.** У справжньому режимі (зріз 2) текст джерел, який обрано для аналізу, **передається провайдеру моделі** через API. На комп'ютері власниці залишається лише база кейсів.
- **Для навчальних і контрольних перевірок використовуємо лише синтетичні матеріали.** Реальні інтерв'ю, персональні чи комерційно чутливі дані до провайдера не передаємо, доки власниця окремо не вирішить інакше (умови провайдера щодо зберігання й використання даних треба прочитати до цього рішення — я їх не перевіряв).
- **Програмний запобіжник (запропоновано для зрізу 2):** кожне джерело має позначку походження — `synthetic` / `real` / `demo_script`. Справжній запуск агента **відмовляється** передавати джерело з `origin=real`, поки людина не ввімкнула для кейсу окрему згоду «дозволяю передачу реальних матеріалів провайдеру» (запис у журналі). Це захищає від випадкової передачі, а не замінює обережність аналітика.
- **У зрізі 1 позначка вже є**: поле `origin` збережено, форма додавання джерела за замовчуванням ставить «синтетичний», а підказка нагадує про правило. Запуску моделі в зрізі 1 немає, тому нічого нікуди не передається.
- **Розміщення (D6) лишається відкритим**; вибір між варіантами А і Б не змінює правила вище, але варіант Б додає ще одного одержувача даних (хостинг).

### Деморежим та справжній режим — чітко розділені (D9)

| | Деморежим | Справжній режим |
|---|---|---|
| Що це | Заздалегідь підготовлені відповіді-заготовки для перевірки **програмної логіки** | Виклик реальної моделі |

## 4. Модель даних (D10)

Принцип: **нічого важливого не перезаписується.** Змінення = новий запис.

| `finding_resolution` (зріз 3) | Рішення аналітика щодо знахідки агента 2: копія знахідки, «відхилено», пояснення, хто, коли, ID запуску, ID погодження, хеш пакета (D31) | Ні (тільки додавання) |
| `bpmn_artifact` | Результат агента 2: структура, XML, карта «крок ↔ елемент», результати перевірок, погоджена версія, на основі якої створений, стан (`generated` / `technical_ok` / `needs_fix` / `accepted` / `stale`) | Стан — так; вміст — ні |
| `audit_log` | Журнал подій (хто, що, коли). Без прихованих міркувань моделі | Тільки додавання |

### Зміст версії AS-IS (усередині `as_is_version.content`)

Відповідає спец. §6. Кожне з нижче має **стабільний ID**, що не змінюється між версіями:

- **Бізнес-контекст і межі:** проблема, замовник, ефект, тригер, вхід, фактичне завершення, результат.
- **Ролі.**
- **Кроки:** ID, роль, дія, умова входу, вхідний артефакт (якщо є), результат, наступні кроки з умовами, джерела.
- **Початковий крок:** `entry_step_id` — явний ID кроку, що виконується першим після тригера (розділ 5б, D27). Не виводиться з порядку кроків.
- **Відомі обмеження** (не окреме поле, а похідний перелік): відкриті некритичні питання, відкриті гіпотези, оцінки замість метрик — лишаються в погодженому пакеті й показуються в підсумковому документі (розділ 5, D28).
- **Проблеми та вплив:** симптом / можлива причина / наслідок окремо; оцінки позначені як оцінки.
- **Твердження (claims):** ID, текст, **тип**, джерело + **точний фрагмент** (зсув у тексті), область застосування, статус перевірки.
  Типи: `source_fact` · `analyst_confirmed` · `hypothesis` · `improvement_proposal` · `unknown`. Це і є збереження походження: пропозиція TO-BE не може бути записана як `source_fact`.
- **Гіпотези:** ID, автор (аналітик/агент), статус, докази за/проти, спосіб перевірки, історія змін статусу.
- **Питання:** ID, формулювання, вплив, **критичність**, адресат, відповідь, джерело закриття. Зміна критичності вимагає поле «пояснення аналітика».
- **Конфлікти:** пара тверджень із різних джерел, показані обидві.

### Програмні перевірки джерел
Код перевіряє, що цитата **дослівно є** в тексті названого джерела. Це доводить існування фрагмента, а **не** те, що він підтверджує висновок. Це обмеження явно показується в інтерфейсі (спец. §4).

## 5. Версії й стани (D11)

### Версії
1. Кожна зміна (від агента чи людини) створює **нову** версію. Правки аналітика — окрема версія, а не втручання у стару.
2. Запит на зміну містить `base_version_id`. Якщо за цей час з’явилася новіша версія — сервер повертає конфлікт (409), нічого не затираючи.
3. **«Прийняти робочу версію»** — це позначка аналітика, що чернетка його влаштовує. **Це не погодження AS-IS** (спец. §2, п. 5).
4. **Погодження** прив’язане до `version_id` + хеш + автор + час. Хеш перераховується з бази при кожній перевірці.

### Стани кейсу

```
Дослідження ─(передати на погодження)─► На погодженні ─(погодити)─► AS-IS погоджено
    ▲  ▲                                     │                            │
    │  └──────(повернути на доопрацювання)───┘                  (створити BPMN)
    │                                                                      ▼
    ├──(нове джерело / зміна змісту / неоднозначність від агента 2)── BPMN на перевірці ─(прийняти)─► Завершено
    └─────────────── із «На погодженні» та «AS-IS погоджено» ───────────────┘
```

- Нове джерело або зміна змісту в станах «На погодженні», «AS-IS погоджено» і «BPMN на перевірці» **автоматично повертає кейс до «Дослідження»**. Чинне погодження позначається `superseded` з причиною, **не видаляється**.
- Помилка лише в схемі: кейс лишається «BPMN на перевірці», артефакт отримує стан `needs_fix`; повторна генерація створює **новий** артефакт із того ж погодженого AS-IS. Погоджений AS-IS не змінюється.
- Неоднозначність від агента 2: питання записується до кейсу, кейс → «Дослідження».
- **Технічний стан запуску** (`queued/running/done/error`) — окреме поле в `run`, не впливає на стан кейсу.

### Невідоме не стає фактом: невизначені переходи (D20)

Крок може мати перехід зі значенням **«невідомо»** (`?`). Це не завершення (END) і не крок: це позначка, що продовження процесу не з’ясовано. Питання, що стосується переходу, зберігає зв’язок «крок + умова».

| Правило | Наслідок |
|---|---|
| Питання про перехід автоматично робить його «невідомо» | Опис не стверджує факту, який ще не з’ясовано |
| Відкрите питання, а перехід поданий як встановлений (наприклад END) — **суперечність** | Критична прогалина; передача на погодження й погодження заблоковані |
| Перехід «невідомо» без питання, з відкритим або вже закритим питанням | Критична прогалина (у другому випадку: «оновіть крок відповідно до уточнення») |
| Питання посилається на перехід, якого в описі немає (змінено умову чи крок) | Критична прогалина |
| Знизити критичність питання про перехід | Невизначений перехід усе одно блокує |
| Агент намагається замінити «невідомо» на встановлений перехід при відкритому питанні | Зберігається «невідомо», конфлікт показано |
| Погоджена версія з невизначеним переходом | Серверний дозвіл BPMN відхиляє запит (захист у глибину) |

Закриття питання уточненням **саме по собі не змінює** перехід: аналітик має явно оновити крок. Це свідоме: система не вгадує, як уточнення ляже на схему процесу.

### Класи невизначеності: що блокує, а що може лишитися (D28, **погоджено власницею 30.09.2026**)

**Правило.** **Некритичні прогалини можуть залишатися в погодженому AS-IS. Невизначеність, яка заважає побудувати коректний потік, блокує BPMN.**

| Клас | Приклади | Погодження | Побудова BPMN | Як відображається |
|---|---|---|---|---|
| **K1. Заважає побудувати коректний потік** | невизначений перехід; відсутній чи невизначений початковий крок; умови, які неможливо прочитати як взаємовиключні й вичерпні; крок без виходу чи недосяжний; перехід на неіснуючий крок; кілька умов без визначеної семантики; `[TO DEFINE]` у тексті; кілька точок входу (v1: `unsupported`); потрібен непідтримуваний елемент (D21) | блокує (прогалини щодо ходу процесу, спец. §7) | **блокує завжди**, навіть якщо AS-IS погоджено | блок «Критичні прогалини»; питання (D20) |
| **K2. Некритична** | відкрите некритичне питання, не пов’язане з потоком; відкрита гіпотеза про причину; відсутня числова метрика при дослідженому впливі; оцінки тривалості; непрочитане необов’язкове джерело (попередження); конфлікти правок (попередження) | **не блокує**: лишається в погодженому AS-IS | **не блокує** | блок «Статус перевірки чернетки» (попередження) → у погодженому пакеті як **«відомі обмеження»** → у підсумковому документі |

**Як відрізняємо.** (1) Клас визначає **зв’язок із потоком**, а не позначка «критичне»: питання, пов’язане з кроком чи переходом (D20), — K1 незалежно від позначки; зниження критичності K1 його не знімає. (2) Щоб зняти K1, треба **з’ясувати факт** (закрити питання й оновити крок). (3) K2 не потребує пояснення для погодження, але видимий: відомі обмеження показуються аналітику при погодженні й лишаються в пакеті.
**Коли K1 виявлено після погодження** (структурною перевіркою чи агентом 2): BPMN не будується; для неоднозначності кейс повертається до «Дослідження» з питанням (розділ 1в), для непідтримуваного елемента AS-IS лишається погодженим (D21).

**Стан реалізації (зріз 1):** невизначені переходи як K1 і некритичні питання як K2 уже працюють (тест `tests/uncertainty.test.ts`); явний початковий крок і смислові знахідки — у зрізі 3.

### Передумови для «передати на погодження» (перевіряє код)
- версія прийнята аналітиком як робоча і є **найновішою**;
- версія охоплює **всі** джерела кейсу (немає непрочитаних чи нових);
- жодного обов’язкового джерела зі статусом читання ≠ `ok`;
- немає відкритих питань критичності «критичне» (і про хід процесу);
- структурна повнота: у кожного кроку є роль, дія, результат, наступний крок або кінець; межі й ролі заповнені; у проблем є вплив (або явно «метрики немає»);
- усі зміни критичності мають пояснення.

Змістову повноту («чи зрозумілі умови й винятки») оцінює **людина** — список для перевірки в інтерфейсі, не автоматичний висновок.

### 5б. Початковий крок процесу (D27, **погоджено власницею 30.09.2026**)

**Визначення.** **Початковий крок — це крок, який виконується першим після тригера процесу.** Він задається **явним полем `entry_step_id`** у змісті версії AS-IS (ID існуючого кроку). Це частина змісту: змінення поля створює нову версію, входить у хеш і потребує нового погодження.

**Що заборонено.** Визначати початковий крок за порядком рядків чи за порядком у списку (перший, найменший ID, «той, у який ніхто не веде» тощо). **Порядок кроків у списку не має змістового значення** (лише для показу), і код ніде не може використовувати «перший рядок» як запасний варіант.

| Правило | Наслідок |
|---|---|
| Поле обов’язкове для передачі на погодження | Немає поля — критичний блокер `ENTRY_MISSING`; погодити версію без нього неможливо |
| Має вказувати на існуючий крок | Інакше `ENTRY_BAD_REF` |
| Усі кроки досяжні від початкового | Інакше `STEP_UNREACHABLE` із переліком кроків (крок, у який ніхто не веде, — не початок, а помилка чи неповнота опису) |
| Початковий крок один | Процес із кількома точками входу v1 не описує: аналітик фіксує обмеження, а побудова BPMN — `unsupported` (D21, кілька початкових подій) |
| Сервер перевіряє поле повторно при запуску BPMN | Пакет без поля не дає дозволу (захист у глибину) |
| Початкова подія схеми: назва = `boundaries.trigger` дослівно; єдина вихідна лінія веде **точно** в початковий крок | Зворотна перевірка (розділ 1а) відхиляє інший початок |
| Явний вибір | Аналітик обирає крок у списку («Початковий крок» на вкладці «Редагувати»); агент 1 може **запропонувати** кандидата з цитатою, підтверджує людина. Агент 2 його не задає |
| Зміна порядку кроків у списку | Не змінює ні потік, ні схему (тест: та сама схема після перестановки) |

**Перевірки потоку для нашого процесу v1 (реалізовано 30.09.2026; D27, D34).** Кожна блокує **передачу на погодження, саме погодження і серверний дозвіл BPMN**; пояснення називає конкретні кроки й причину:

| Код | Що перевіряє | Приклад пояснення |
|---|---|---|
| `ENTRY_MISSING`, `ENTRY_BAD_REF` | Початковий крок заданий і існує | «Початковий крок не визначено … Система не вибирає його за порядком рядків» |
| `STEP_UNREACHABLE` | Кожен крок досяжний від початкового | «Недосяжні кроки: S3 («…»). Від початкового кроку S1 немає жодного шляху до нього» |
| `STEP_NO_EXIT` | З кожного досяжного кроку можна дійти до завершення (END); замкнений цикл без виходу — помилка | «Замкнений цикл без виходу: S1 → S2 → S1. З кроків S1, S2 неможливо дійти до завершення» |

**Цикли з виходом дозволені** (повернення на доопрацювання, «повторити»): вимога лише в тому, щоб із циклу існував шлях до завершення. Перехід «невідомо» для цієї перевірки вважається можливим виходом, бо його вже блокує окреме правило невизначених переходів (D20): прогалину не дублюємо.

**Старі записи без початкового кроку (реалізовано).** Поле необов’язкове в схемі, тож існуючі версії читаються як раніше; вони **не переписуються й не видаляються**, а система **нічого не вибирає мовчки**:
- версія без поля має явну критичну прогалину «запис створено до появи цього поля» з вибором початкового кроку прямо в блоці прогалин;
- у погодженому записі без поля BPMN заблоковано, а рекомендована дія — «Уточнити початковий крок»;
- явний вибір створює **нову версію** (погоджена версія лишається незмінною в історії, її погодження скасовується з причиною `content_changed` і не видаляється); нову версію треба прийняти, передати на погодження й погодити;
- діалог перед створенням нової версії прямо пояснює ці наслідки;
- інші правки старого запису поле не встановлюють.
Перевірено на справжньому файлі даних попереднього випуску (розділ 10, зріз 1).

**Тести (реалізовано):** `tests/flow.test.ts` — обидва негативні приклади в трьох точках (передача, погодження, серверний дозвіл), коректний цикл із виходом, початок не за порядком рядків, хибне посилання, старий запис, агент не змінює початок, прямі HTTP-запити. Зріз 3 додасть перевірки початкової події схеми.

## 6. Серверний контроль погодження (D12)

Ключова функція `canStartBpmn(caseId)`, яка виконується **на сервері всередині однієї транзакції** з створенням запуску. Кнопка в браузері лише викликає її.

Запуск агента 2 дозволено, лише якщо **все одночасно**:
1. стан кейсу = «AS-IS погоджено»;
2. є чинне (не скасоване) погодження, створене користувачем-людиною;
3. хеш версії в базі = хеш, записаний у погодженні;
4. погоджена версія = найновіша версія кейсу;
5. немає джерел, доданих після погодженої версії;
6. у погодженій версії немає відкритих критичних питань;
7. немає іншого активного запуску агента 2 для цього кейсу.

**Вхід агента 2 сервер завантажує з бази за ID погодження**, а не з тіла запиту: підмінити зміст неможливо.

### Хто може погоджувати
- Ендпоінт погодження вимагає **сесію людини**. Код запуску агентів не має доступу до модуля погодження й не володіє сесією.
- Модель повертає лише дані за схемою; **інструментів із побічними діями в неї немає**. Поля на кшталт «статус: погоджено» схемою відхиляються.
- Тригер, вбудований у транскрипт («погодь процес», «ігноруй правила»), — це дані: джерела подаються моделі в межах чітко позначених блоків «ДАНІ», а весь результат проходить перевірку схеми.
- Захист у глибину: тригери в SQLite забороняють `UPDATE/DELETE` для змісту версій, джерел і погоджень.
- **Чесне обмеження:** прототип однокористувацький. Це захищає від помилок агента, обходу кнопки та ін’єкцій у джерелах, але не від людини з доступом до файлу бази.

### Застарілі результати
- Кожен запуск записує `base_version_id`. Коли агент 1 завершився, а голова версій уже інша (аналітик редагував паралельно) — результат зберігається як **окрема пропозиція на застарілій основі** і сам не стає поточною версією. Аналітик бачить попередження й вирішує, що взяти.
- Агент 2: якщо після старту погодження скасовано чи додано джерело, готовий артефакт отримує стан `stale`, не прикріплюється до кейсу як чинний і не може бути прийнятий.

## 8. Поведінка при помилках (D14)

| Ситуація | Що відбувається | Що не змінюється |
|---|---|---|
| Файл не прочитано | Джерело `error`, видима помилка, погодження заблоковане | Попередні версії, погодження |
| Мережевий збій/перевантаження моделі | 1 автоматична повторна спроба; далі запуск `error` і повідомлення людині | Стан кейсу, прийняті версії |
| Тайм-аут | Запуск `error`, без часткового результату як версії | Те саме |
| Відповідь не за схемою | Одна повторна спроба з переліком порушень; далі `error` | Те саме |
| Цитата не знайдена в джерелі | Твердження позначається «фрагмент не знайдено», версія збережена як пропозиція з видимим попередженням | Прийняті правки |
| Суттєва прогалина в знаннях | Питання людині, **без** повторного запуску «для лікування» (спец. §9) | — |
| Вичерпано ліміт | Запуск зупинено, повідомлення | — |
| Агент 2: модель недоступна / тайм-аут / відповідь не за схемою | Друга стадія зупиняється (`error`), артефакт не створюється; можна повторити запуск (D32); режиму «без смислової перевірки» немає | Погоджений AS-IS і погодження |
| Конфлікт версій при збереженні | 409, аналітик бачить обидві версії | Обидві версії |

Журнал запуску (спец. §9): агент, версія інструкції, режим, модель, вхідна версія, опрацьовані джерела, час, результати перевірок, помилки, вихідна версія. Журнал погоджень — окремий.

## 9. Коротка картка (D15, порядок блоків оновлено — D33)

**Порядок блоків (погоджено власницею 30.09.2026):** шапка (назва, версія, текстовий статус, режим) → 1) **Суть** → 2) **Предметний опис AS-IS із вкладками** → 3) **Критичні прогалини та рекомендована наступна дія** → 4) **Головні зміни від попередньої версії** → 5) **Перевірки готовності** (короткий підсумок, деталі розгортаються).

**Опис AS-IS (вкладки).** Спершу читач має зрозуміти, навіщо існує процес, для кого він створює результат і яку бізнес-потребу досліджуємо; далі — тригер, межі й завершення; потім послідовність дій.
- **1-ша, відкрита за замовчуванням: «Бізнес-контекст і межі»** — навіщо існує процес (бізнес-потреба, замовник, для кого результат) → результат процесу → тригер, вхід, фактичне завершення, початковий крок → ролі. Якщо щось не з’ясовано, це показано явно («Не з’ясовано…»). Використовуються наявні поля; окремих полів «замовник» і «користувач результату» немає, про що картка нагадує.
- **2-га: «Кроки процесу»** — початковий крок (▶), таблиця кроків, невизначені переходи виділено з посиланням на питання.
- Далі: «Твердження й докази», «Проблеми й вплив», «Гіпотези», «Питання», «Джерела», «Редагувати», «Історія».

**Критичні прогалини** — завжди на екрані: відкриті критичні питання, невизначені переходи, суперечності, початковий крок, недосяжні кроки, цикли без виходу. Це **змістові** прогалини. Під ними — одна рекомендована наступна дія (заблокована показує причину).

**Головні зміни:** коротка змістовна різниця («було «…», стало «…»», зміна переходу, закрите питання з відповіддю, початковий крок); п’ять на екрані, решта — «усі зміни».

**Перевірки готовності:** короткий підсумок («Чернетка готова / ще не готова», кількість пройдених і ні, назви тих, що не пройдено); деталі (сім перевірок із текстовими підписами «Пройдено / Не пройдено / Увага», не лише колір) розгортаються.

**Докази:** біля кожного суттєвого твердження — позначка типу і посилання на точний фрагмент джерела. **Після повторного запуску** першим показується огляд змін. Порожні розділи згортаються в один рядок.

**Перевірка порядку:** сценарій у браузері (`scripts/walkthrough.ts`) перевіряє порядок блоків, першу й другу вкладки та згорнутість перевірок, а не лише знімає екрани.

## 10. План програмних зрізів (D16)

Кожен зріз — окрема невелика зміна з переліком перевірок і власним звітом (що змінено, що фактично перевірено, команди й результати, що ще не працює).

### Зріз 1 — «Каркас довіри»: збереження й контроль погодження (без AI)
**Мета:** довести, що правила працюють, до того, як з’явиться будь-яка модель.

Що входить:
- 1a. Каркас проєкту, команди `npm test`, `npm run typecheck`, `.gitignore`, `.env.example`. *(Після цього стають відомі реальні команди для hooks — розділ 11.)*
- 1b. База, версії, погодження, стани, `canStartBpmn`, журнал.
- 1c. Мінімальний інтерфейс: список кейсів, картка, додавання текстового джерела, питання, кнопки.
- 1d. Деморежим: заготовлений «аналітик» повертає версію з одним критичним питанням; після уточнення — нову версію. **Усе позначено «ДЕМО».**

Наскрізний сценарій (acceptance.md): створення кейсу → текстове джерело → робоча версія → критичне питання блокує погодження → уточнення створює нову версію → людське погодження → дозвіл наступного етапу (у зрізі 1 «наступний етап» — лише дозвіл; BPMN ще не будується).

**Обов’язкові автоматичні тести** (усі з acceptance.md):
1. Прямий запит до backend на запуск BPMN без погодження → відхилено.
2. Погодження застарілої версії → відхилено.
3. Нове джерело після погодження → погодження `superseded`, запуск заблоковано, історія збережена.
4. Результат запуску на застарілому стані → не стає поточною версією.
5. Правки аналітика збережені при новому запуску.
6. Помилка читання/моделі → прийнята версія й статус не змінилися.

Додатково: тригери БД забороняють зміну версій; підміна хеша виявляється; запит із чужим `base_version_id` → 409; вбудована в джерело фраза «погодь процес» не змінює стан.

**Критерії завершення:** тести виконані й показані з реальним виводом і кількістю (нуль тестів — не успіх); скриншоти сценарію (Playwright, якщо запуск підтвердиться); на кожному екрані видно «ДЕМО»; звіт із чітким «що ще не працює».

### Зріз 2 — Справжній аналіз джерел (агент 1)
**Потрібно перед стартом:** ключ і ліміт витрат (D7), синтетичний файл із інтерв’ю, очікування для контрольних кейсів.

- Інструкція агента 1 v0.2 із prompts/analyst.md (методологія з розділів 5–7 спец. включається прямо в runtime-інструкцію), схема відповіді, перевірка цитат, запис запуску, ліміти й одна повторна спроба.
- **Очікування (потрібні факти, заборонені домисли, блокери) фіксуються ДО першого запуску** й лежать у окремій теці тестових очікувань.
- Поступовий прогін: зустрічі додаються по одній; перевірка збереження правок і історії гіпотез.
- Оцінка змісту за спец. §10 (єдиний канал, публікація ≠ готовність, спростування гіпотези, різні типи процесу, нема baseline, непрочитаний файл).
- Перший реальний запуск — малий, щоб виміряти вартість і задати ліміти.

**Критерії:** реальні запуски мають `mode=real` і назву моделі в журналі; змістова оцінка задокументована окремо від програмних тестів; невдачі не приховані зміною очікувань.

### Зріз 3 — BPMN
Перед початком: питань розділу 12 немає. Показ результату 3a погоджено: тестові пакети, згенеровані `.bpmn`/`.drawio` як файли й знімки переглядача, без окремої кнопки обходу. Уже погоджено: D29–D32 (роль агента 2; водяний знак bpmn.io; відхилення зауваження; збій моделі), D26 (`.bpmn` основний, `.drawio` експорт), D27 (явний початковий крок), D28 (класи невизначеності), збереження оригіналів і перенесення логіки на TypeScript (D22).

- **3a. Без AI.** На вручну підготованому погодженому пакеті:
  1. використання `entry_step_id` у генераторі й зворотній перевірці (поле й структурні перевірки потоку вже реалізовано, розділ 5б);
  2. **генератор на TypeScript** (без глобального стану, у пам’яті, унікальні ID, екранування, перевірка входу) + `bpmn-auto-layout@2.0.0-alpha.2` як бібліотека;
  3. **зворотна перевірка** за розділами 1а–1б;
  4. **порівняння з вашим Python-ланцюгом** з `reference/bpmn-pipeline/original/`: на «здорових» входах вихід збігається з еталоном (за узгодженим порядком нормалізації); на нездорових наш генератор відмовляє з поясненням, еталон мовчки губить;
  5. основний артефакт `.bpmn`, переглядач у браузері (з водяним знаком bpmn.io, D30), карта «крок ↔ елемент»;
  6. експорт `.drawio` із власною звіркою (ID кроків у клітинках);
  7. ізоляція запусків: ≥20 паралельних пар без змішування;
  8. **набір негативних прикладів** (усі мають бути відхилені): лапки в дії/ролі/умові/назві пулу; керівний символ; повторні ID; кілька умов в одну ціль; перехід на неіснуючий крок; крок без входу; глухий кут; додана задача; підмінена умова; не та доріжка; втрачений цикл; зайвий таймер/паралельний шлюз; втрачена геометрія; файл на застарілій версії; початок у не тому кроці; немає початкового кроку;
  9. правила D28: K2 не блокує ні погодження, ні BPMN; K1 блокує BPMN.
- **3b. Агент 2 v0.2** за розділом 1в: смислова перевірка, знахідки за схемою, перевірка цитат кодом, `blocks_flow` → очікування рішення аналітика (уточнити AS-IS або відхилити з поясненням, D31), `unsupported` за D21, збій моделі зупиняє етап із повтором (D32), деморежим без імітації. Тексту схеми агент не повертає (тест: відповідь із полем `action`/`role`/`condition` відхиляється).
  Тести D31–D32: відхилення без пояснення не записується; `UNSUPPORTED_CANDIDATE` відхилити неможливо; відхилення записується з копією знахідки, хешем і ID запуску та видно в історії й підсумковому документі; **після відхилення кодові перевірки не обходяться** (підміна хеша, невизначений перехід, відсутній початковий крок, невдала зворотна перевірка — усе блокує); модель недоступна → `error`, артефакт не створено, стан кейсу й погодження без змін, повтор створює новий запуск із `retry_of`; у продуктовому шляху немає гілки без завершеної смислової перевірки.
- **Людське приймання:** карта «крок ↔ елемент» і явне попередження, що технічна перевірка не доводить змістову правильність.

**Критерії:** `.bpmn` відкривається в переглядачі; кожен елемент має ID кроку; зайвих кроків немає; зміст збігається з погодженим пакетом дослівно (перевірка чиста); початковий крок — явно заданий; неоднозначність повертає питання, а не вигаданий крок; **непідтримуваний елемент повертає пояснення обмеження (`unsupported`), а не змінену логіку процесу**; порушення перевірки → файл не видається; усе, що створює файли й перевіряє відповідність, — код (тест: у шляху генерації немає викликів моделі).

### Зріз 4 — Наскрізна перевірка й підсумковий документ
- Позитивний кейс (з позначеними синтетичними уточненнями) і негативний (критичний факт вилучено з усіх матеріалів **і** з оглядів/попередніх версій).

## 11. Hooks (D17; пропозиція, **нічого не активовано**)

Мета — допомога розробці, а не захист продукту (його захищає backend). Усі команди-кандидати з’являться лише після зрізу 1a; до того hooks не створюються, щоб не було пустих перевірок «завжди успішно».

| Hook | Команда | Коли додати | Обов’язкова перевірка перед активацією |
|---|---|---|---|
| SessionStart | `npm ci` за відсутності `node_modules` (без друку змінних середовища) | Після появи `package-lock.json` (1a) | Нова cloud-сесія: залежності поставлені; випадок без мережі дає зрозуміле повідомлення; тайм-аут |
| PostToolUse (Edit/Write у `prompts/**` та `src/schemas/**`) | Скрипт перевірки: інструкції мають обов’язкові розділи, схеми валідні (JSON/zod) | Коли скрипт існує (зріз 2) | Спрацьовує на потрібній події; проходить на правильному файлі; відхиляє відомий дефект |
| Команда `npm test` + `npm run typecheck` | Звичайні команди, не hook | 1a | Працюють без жодних hooks |
| CI (GitHub Actions) | Ті самі `npm test` і `typecheck` при push | Зріз 1 | Перший запуск на гілці; **це файл у репозиторії, не публікація сервісу** |
| PreToolUse (кандидат, лише за згодою) | Блокувати правки в теці очікувань тестів без явної вказівки | Після зрізу 2, якщо власниця захоче | Може заважати законним змінам очікувань; тому лише за вашим рішенням |
| Stop | Не використовується | — | Лише за доказаної користі |

Перевірка «hook завантажується в новій cloud-сесії» виконується окремо; поки її не зроблено, hook не називається активним. Hooks працюють в одному репозиторії; правила CLAUDE.md — інструкція, а не гарантована заборона, тому критичні заборони лишаються в коді backend.

**Агенти.** Продуктових агентів рівно два. Додаткових агентів для перевірок не створюю: технічні перевірки — звичайний код. Семантична перевірка «чи цитата підтримує висновок» відкладена: додаю лише якщо зріз 2 покаже, що без неї помилки не видно.

## 13. Припущення, ще не перевірені

1. **`node:sqlite`** експериментальний; API може змінитися. Запобіжник: тонкий шар доступу до бази, швидка заміна на `better-sqlite3`.
2. Чи **bpmn-js** відкриває XML, згенерований власним кодом, і чи **автоматична розкладка** дає читабельну схему на реальних кейсах.
3. Чи запускається **Playwright/Chromium** у cloud-сесії для скриншотів.
4. Чи **hooks** справді завантажуються в нових cloud-сесіях (твердження з docs/hooks-plan.md я не перевіряв заново).
5. Чи ваш акаунт дозволяє отримати API-ключ і як влаштована оплата.
6. Ціна, ліміти й вибір моделі — невідомі до вимірювання на зрізі 2.
7. Якість української мови й **точність дослівних цитат** обраної моделі.
8. Чи достатньо структурного вводу (JSON кроків) для однозначного BPMN на реальному кейсі.
9. Вхідних синтетичних даних у репозиторії немає, тому позитивний/негативний кейси поки не можуть бути описані.
10. Чи достатньо однокористувацької моделі й локального запуску для ваших потреб.

---
11. Вигляд і читабельність результату **в самому draw.io** (накладання, довгі підписи): перевірено лише склад XML.
12. Поведінка ланцюга й лейаутера на **Windows**, на процесах понад 60 кроків, з кількома пулами й інших версіях лейаутера.
