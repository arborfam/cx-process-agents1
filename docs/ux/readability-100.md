# Читабельність продуктового інтерфейсу: до / після

Перевірка: `node --import tsx scripts/verify-readability.ts after` — **67/67**.
Два різні процеси з довгими текстами (підтримка клієнтів і закупівлі), усе створюється через
інтерфейс; агенти — підставні клієнти, оголошені у файлі перевірки. **Платних викликів не було.**
Порівняльний прогін «до» зроблено на коді комміта `edb36c8` тим самим сценарієм
(`… verify-readability.ts before`).

Знімки: `docs/ux/shots/readability/` — пари `before-*` / `after-*`.

## 1. Огляд

| | До | Після |
|---|---|---|
| «Коротко» | один абзац `summary` цілком: бізнес-контекст, межі, послідовність і перелік вузлів злиті в суцільний текст; перелік із джерела втратив пункти й читався як «… затримується: - очікування … ; - повторне …» | структуровані рядки: **Процес**, **Навіщо цей процес**, **Початок**, **Завершення**, **Обсяг опису**; довге поле не обрізається «першими N символами», а веде на повний текст |
| Останній завершений запуск | окрема картка на пів екрана | згорнутий рядок; «виконується» лишається розгорнутим |
| «Потребує уваги» | один список упереміш | чотири групи: **Бізнес-невідоме**, **Потрібне ваше рішення**, **Технічні прогалини опису**, **Відкриті питання — не блокують** |
| Висота сторінки огляду (1440×900) | 1436 px (CX) / 1407 px (закупівлі) | **1119 px / 1090 px** |

Критичне питання лишилось у червоному рядку над усім — його видно без жодного розкриття.
Шрифт не зменшувався: виграш дає структура й згортання довідкового, а не дрібніший текст.

**Мета дослідження.** Окремого поля «мета дослідження» в описі немає. Нічого не вигадано: на огляді
показано `business_context` під підписом «Навіщо цей процес», і лише коли його заповнено;
на вкладці «Бізнес-контекст» це сказано прямо.

## 2. Структурований зміст на вкладках

- **Бізнес-контекст** — розділи «Процес», «Мета», «Межі процесу», «Учасники». Повний опис процесу
  тепер видно саме тут, абзацами; перелік, який уже був у тексті, став справжнім списком.
  Розбиваємо **лише по рядках**: речення й крапки з комою не чіпаємо, бо це змінило б зміст.
  Довгий текст має «Показати повністю», і **всередині розкритого** лишаються абзаци й списки.
- **Кроки** — замість таблиці з п'яти колонок окремі блоки: ID, дія, виконавець, далі окремими
  рядками «Умова входу», «Результат», «Далі» з **умовою переходу окремим рядком**. Деталі кроку —
  під розкриттям. Унизу кроку — «Докази: N» з назвами джерел.
- **Твердження** — один запис на твердження з явним типом: «Факт із джерела», «Гіпотеза»,
  «Невідоме», «Пропозиція покращення», «Рішення користувача». Підстава названа джерелом, а стан
  перевірки цитати («фрагмент знайдено» / «⚠ НЕ знайдено») лишився видимим.
- **Питання** — текст → «Чому важливе» → «Кому адресовано» → «Стан» → «Хто поставив» → дія.
  Прив'язки до кроків і їхня історія розкриваються окремо. Форма закриття питання розгорнута
  для критичних і згорнута для некритичних.
- **Джерела** — запис на джерело: назва (повний текст відкривається окремо), тип, походження,
  опрацювання, враховано у версії.
- **Схема** — угорі компактний стан: «Смислова перевірка» і «Схема», з переходом до побудованої
  схеми. Чинні блокування лишились на видноті (заголовок «Чинні блокування побудови»), зауваження
  з уже ухваленим рішенням згорнуто в «Історію».
- **Історія** — короткі записи «що змінилося / коли / ким»; режим, вид версії, інструкція, спроби,
  помилки — всередині запису.

## 3. Універсальні формулювання

Перевірено походження кожної фрази:

| Фраза | Звідки | Що зроблено |
|---|---|---|
| «аналітикиня» біля версії | шаблон інтерфейсу (`CREATED_BY`) | «користувач» |
| «Погодила аналітикиня» | шаблон історії | «Версію погоджено» |
| «прийнята аналітиком» | шаблон історії | «Прийнято: так/ні» |
| «Підтверджено аналітиком», «Підтверджений висновок аналітикині», «відредаговано аналітикинею» | підписи типів (`CLAIM_TYPE_LABEL`, `ANSWER_CONTENT_TYPE_LABEL`) — у базі зберігається лише код | «Рішення користувача», «Підтверджений висновок користувача», «відредаговано користувачем» |
| «потрібне рішення аналітикині», «не прийнято аналітиком», «конфлікти між правками аналітика й агента» | обчислювані повідомлення блокерів і змін | «потрібне ваше рішення», «ще не прийнято», «розбіжності між вашими правками й пропозиціями агента» |
| «Я врахувала нові джерела» | підпис прапорця форми | «Нові джерела враховано в цій версії» |
| підпис людини в нових записах | **константа сервера** `Actor.name` | «Користувач» |

**Чого НЕ змінювали:** текстів джерел, цитат, збереженого змісту версій. Пояснення розбіжностей
(`conflicts[].note`) зберігається в описі — воно показується як є, під заголовком «Розбіжності між
правками користувача та агента», і старі записи зберігають те формулювання, з яким їх створено.
Уже збережені імена авторів (`actor_name`, `approver`, `decided_by`) не переписуються: це
зафіксоване авторство, і воно показується в метаданих та історії.

## 4. Докази й технічні посилання

- `src_…` більше не з'являється в тексті: крок показує «Докази: N» з назвами джерел, твердження —
  назву джерела з переходом до фрагмента. Ідентифікатор лишається в підказці елемента.
- Службовий код на початку причини (`NOT_APPROVED_STATE: …`) прибрано з рядка й перенесено
  в підказку; сам текст причини не скорочено.
- Нічого з походження не видалено, прив'язок не вигадано, критичні невизначеності не приховано:
  «⚠ фрагмент НЕ знайдено», «НЕВІДОМО» на переході й червоний рядок критичного питання лишились.
  Історичний перелік невідомого не видається за чинні блокування — на вкладці «Схема» вирішене
  лежить в «Історії», а чинне має власний заголовок.

# Доповнення D101: довгий абзац без переносів рядків

D100 не закривав вихідний випадок. Текст без жодного переносу рядка (723 символи) виводився
**цілком** перед «Показати повністю», а всередині розкриття повторювався: перший вузол `longText()`
показувався незалежно від довжини.

**Що змінено**

1. Понад межу текст показується **один раз** — лише розкриття з назвою й розміром
   («Показати повний текст · 723 симв.»), усередині структурований оригінал.
2. Перелік усередині одного рядка («…затримується: - очікування …; - повторне …; - ручне ….»)
   відображається списком. Маркер — дефіс після початку рядка або «:»/«;», і лише коли маркерів
   щонайменше два. Речення після останнього пункту виноситься окремим абзацом.
3. Огляд бере коротке структуроване значення (погоджений короткий підпис початкової події, якщо він
   є), інакше дає назване посилання: «Бізнес-контекст», «Умови початку», «Умови завершення».
   Фрази «Заповнено, текст довгий» більше немає.
4. З інтерфейсу прибрано пояснення будови даних; розділ названо «Бізнес-контекст».

**Знімки випадку:** `after-flat-1-згорнуто.png` (початковий вигляд), `after-flat-2-розкрито.png`
(розкритий текст), `after-flat-3-огляд.png` (огляд того ж кейсу).

**Розбір переліку перевірено на:** дефісі в слові («бізнес-контекст», «AS-IS», «крос-функційна»),
тире в реченні («Процес — це …»), умовах через крапку з комою («якщо А; якщо не Б»), запереченні
в пункті, одному маркері (списком не стає), пунктах із дефісами всередині.

**Відоме обмеження.** Якщо пункт сам містить межу речення (крапка, пробіл, велика літера), текст
після неї буде винесено з останнього пункту окремим абзацом. Для переліків, де пункти — це фрази
без крапок (звичайний випадок), це дає правильний результат.
