## Залишкові обмеження — чесно

1. **Прототип лишається окремо** (`design/prototype/`) як еталон дизайну. Він не є продуктом
   і його самоперевірка доказом роботи продукту не вважається.
2. **Якість відповідей моделі не перевірялась.** Усе перевірено в деморежимі з підставними
   клієнтами. Жодного платного запуску за інструкціями `analyst v0.10` і `bpmn-v0.7` не було.
3. **Пропозиція короткого підпису від агента 1** (`boundaries.trigger_short`) у справжньому
   прогоні не перевірялась: поле є в контракті й в інтерфейсі, але модель його ще не заповнювала.
4. **Збережена таблиця версії 29 не проходить чинний контракт** (колонка `role` у подій і шлюзів).
   Це вада самої таблиці, а не продукту; перевірка працює на адаптованій копії.
5. **Вади геометрії пайплайна** (порожні доріжки, надмірна ширина) не виправлялись — це окрема
   вимога до генератора, а не до подання.
6. **Користувацького тестування не було.** Перевірено, що інтерфейс працює з продуктовими даними
   й правилами; зручність для аналітикині доведе лише спостереження за реальною роботою.
7. **Темну тему відкладено** свідомо, як і в погодженому дизайні.

## Як відкрити оновлений продукт

```
npm ci                 # один раз
npm run demo           # запускає деморежим із синтетичним кейсом
```

У виводі буде рядок виду `http://localhost:3000/login?code=…` — відкрийте його повністю
в браузері. Деморежим не звертається до моделі й нічого не коштує.

Щоб відтворити перевірки:

```
npm test                                             # 827 тестів домену
node --import tsx scripts/verify-product-route.ts    # продуктовий маршрут, CX + закупівля
node --import tsx scripts/verify-v29-navigation.ts   # навігація схемою версії 29
```

Обидва сценарії працюють на тимчасовій базі у власному каталозі, на вільному порту,
і нічого не змінюють у вашій робочій базі.
