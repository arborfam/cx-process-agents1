# BPMN Diagram Pipeline: опис рішення та запит на перенесення в корпоративне середовище

> Статус: робочий прототип, перевірений на реальних процесах. Запит до тех команди — розділ 5.

---

## 1. Що це і навіщо

Інструмент, що перетворює текстовий опис бізнес-процесу на готову BPMN-діаграму у форматі draw.io — з доріжками за ролями, коректною розкладкою та нативними фігурами, без ручного малювання і без правок геометрії.

Проблема, яку він закриває: побудова BPMN-діаграм — одна з найбільш трудомістких частин документування процесів. Попередні спроби автоматизації (генерація XML через LLM, CSV-імпорт draw.io) впирались у два обмеження: LLM ненадійно рахує координати, а вбудовані механізми draw.io не створюють справжніх доріжок (lanes).

Обидва обмеження зняті. Поточний результат: аналітик перевіряє таблицю з ~20 рядків замість малювання діаграми; генерація — одна команда; правки геометрії — нуль (перевірено на процесах нижче).

## 2. Архітектура

Принцип: LLM працює тільки зі змістом процесу. Геометрію рахує спеціалізований алгоритм, склейку виконує детермінований код.

Потік: опис процесу → таблиця (CSV) → BPMN 2.0 XML → BPMN XML з координатами → .drawio

| Крок | Виконавець | Вхід → Вихід | Природа |
|---|---|---|---|
| 1. Зміст | LLM + перевірка аналітиком | опис/транскрипт → таблиця CSV | єдина точка змістовних рішень і єдина ручна перевірка |
| 2. Переклад у стандарт | `table_to_bpmn.py` (~150 рядків, власний) | CSV → BPMN 2.0 XML без координат | детермінований, без бізнес-логіки |
| 3. Розкладка | `bpmn-auto-layout` v2.0.0-alpha.2 (bpmn-io / Camunda, Apache-2.0) | BPMN XML → BPMN XML + DI-координати (включно з пулом і доріжками) | зовнішня спеціалізована бібліотека |
| 4. Упаковка | `bpmn_di_to_drawio.py` (~200 рядків, власний) | BPMN XML + DI → .drawio з нативними фігурами | детермінований, стилі взяті з вихідного коду draw.io |

Ключові властивості:

- **Відтворюваність:** той самий CSV дає побайтово ідентичний .drawio (перевірено, зокрема між різними середовищами).
- **Редагованість:** результат для draw.io не відрізняється від намальованого вручну — нативні BPMN-фігури, справжня вкладеність фігур у доріжки, доріжки в пул.
- **Локалізація помилок:** помилка на діаграмі завжди означає помилку в таблиці. Кроки 2–4 рішень не приймають.
- **Стандарт у середині:** проміжний формат — BPMN 2.0 XML, тож ланцюг не привʼязаний до draw.io (той самий XML відкривається у Camunda Modeler та інших інструментах).

## 3. Контракт таблиці (вхід ланцюга)

CSV, 8 колонок: `id, label, type, role, next, yes, no, assoc`.

| Колонка | Призначення |
|---|---|
| `id` | номер елемента; анотації — n1, n2... |
| `label` | назва кроку (без ком) |
| `type` | `start`, `end`, `xor`, `timer`, `note`, `task` (людська задача), `srv` (автоматична) |
| `role` | виконавець задачі; стає доріжкою. Події/шлюзи успадковують роль від потоку |
| `next` | id наступного елемента; для паралельних гілок кілька id через `\|` |
| `yes` / `no` | лише для шлюзів: гілки «Так» / «Ні» |
| `assoc` | лише для анотацій: id елемента прив'язки |


### Покриття нотації BPU (перевірено синтетичним тестом + 3 реальні процеси)

| Елемент нотації BPU | `type` у таблиці | Статус |
|---|---|---|
| Start / End event | `start`, `end` | підтримано, перевірено |
| Дія: Юзер / Сервіс / Ручна | `task`, `srv`, `manual` | підтримано, перевірено |
| Виключаючий шлюз (АБО) | `xor` | підтримано, перевірено |
| Паралельний шлюз | `and`, розгалуження `next=4\|5` | підтримано, перевірено |
| Таймер | `timer` | підтримано, перевірено |
| Доріжка (Lane) | колонка `role` | підтримано, перевірено |
| Анотація + асоціація | `note` + `assoc` | підтримано, перевірено |
| Повідомлення (Message) | `msg` | підтримано, перевірено |
| Згорнутий підпроцес | `sub` | підтримано, перевірено |
| Проміжні події-посилання (Link) | `linkStart` / `linkEnd` | підтримано; пара мусить мати однаковий `label` (валідується лейаутером) |
| Обʼєкт даних | `data` + `assoc` | підтримано, перевірено |
| Інформаційний ресурс | `db` + `assoc` | підтримано, перевірено |
| Мультикомплексний шлюз | — | **не підтримано** лейаутером (явна помилка UNSUPPORTED_ELEMENT); обхід — комбінація `and` + `xor`. У реальних процесах тестів не зустрічався |

Разом: 19 з 20 елементів нотації BPU.

Правило змісту для LLM-генерації: якщо інформації в описі немає або вона суперечлива — у label ставиться позначка `[TO DEFINE: причина]`, елементи не вигадуються.

## 5. Запит до тех команди

### Контекст і ціль

Прототип працює, але Colab — тимчасова форма доставки: ручне завантаження файлів, немає єдиного місця канонічних версій скриптів, запуск вимагає від аналітика роботи з ноутбуком. Ціль — перенести ланцюг у корпоративне середовище як сервіс, до якого аналітик звертається без технічних дій.

### Scope запиту

1. **Хостинг ланцюга.** Середовище з Python 3 + Node.js, ~400 рядків нашого коду + 1 npm-залежність. Обчислювально легкий: прогін процесу на 25 елементів — секунди, без GPU.
2. **Інтерфейс запуску для аналітика.** Мінімально: аналітик передає CSV → отримує .drawio. Форму інтерфейсу пропонує тех команда (варіанти нижче в відкритих питаннях).
3. **Канонічне зберігання коду** з версіонуванням (репозиторій) і піном залежності `bpmn-auto-layout@2.0.0-alpha.2` до виходу стабільної 2.0.

### Вимоги

- Той самий CSV має давати ідентичний .drawio (детермінованість зберігається).
- Підтримка кирилиці в усіх полях (UTF-8 наскрізно).
- Помилки ланцюга повертаються аналітику в читабельному вигляді (номер рядка CSV / warnings лейаутера).
- Без залежності від локальної машини аналітика.

### Acceptance criteria

- **Given:** аналітик має валідний CSV за контрактом (розділ 3). **When:** передає його через погоджений інтерфейс. **Then:** отримує .drawio, що відкривається в draw.io з доріжками, нативними BPMN-фігурами і без накладань — без жодних дій у терміналі чи ноутбуці.
- **Given:** CSV з помилкою структури (битий id у `next`, невідомий `type`). **When:** запуск ланцюга. **Then:** аналітик отримує зрозуміле повідомлення з місцем помилки, а не мовчазний збій.
- **Given:** той самий CSV запущений двічі. **Then:** результати ідентичні.
