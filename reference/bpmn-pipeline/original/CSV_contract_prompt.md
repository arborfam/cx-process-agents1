# Інструкція: перетворення опису процесу на CSV-таблицю для BPMN-пайплайна

Ти отримаєш опис бізнес-процесу (текст, нотатки або транскрипт зустрічі). Твоє завдання — перетворити його на CSV-таблицю за контрактом нижче. Таблиця піде в автоматичний генератор BPMN-діаграм, тому дотримання формату критичне.

## Формат виходу

Видай **тільки CSV** у кодовому блоці, без пояснень до чи після. Перший рядок — заголовок, рівно такий:

```
id,label,type,role,next,yes,no,assoc
```

## Колонки

| Колонка | Правила |
|---|---|
| `id` | Елементи потоку: 1, 2, 3... Анотації: n1, n2... Дані: d1, d2... |
| `label` | Назва кроку українською. ЗАБОРОНЕНІ коми всередині — заміняй на тире або « / » |
| `type` | Тільки зі словника нижче. Нічого не вигадуй |
| `role` | Виконавець кроку — лише для task/srv/manual. У подій, шлюзів, таймерів — порожньо |
| `next` | id наступного елемента. Паралельні гілки: кілька id через вертикальну риску, напр. `4\|5`. Для xor з 3+ сценаріями: підписані гілки `умова>id` через риску, напр. `до 2500 $>10\|від 2500 до 5000 $>7\|понад 5000 $>9` |
| `yes` | Тільки для xor: id, куди веде гілка «Так» |
| `no` | Тільки для xor: id, куди веде гілка «Ні» |
| `assoc` | Тільки для note/data/db: id елемента, до якого прив'язка |

У кожному рядку всі 8 позицій (порожні — просто пропущені між комами).

## Словник type

| type | Коли використовувати |
|---|---|
| `start` | початкова подія — що запускає процес |
| `end` | завершальна подія; кінців може бути кілька (успіх / відхилення) |
| `task` | крок, який виконує людина |
| `srv` | крок, який виконує система автоматично (Jira automation, скрипт, сервіс) |
| `manual` | ручна робота поза системами |
| `xor` | розвилка з питанням; label — питання зі знаком «?». Дві гілки — yes/no; три і більше сценаріїв — підписані гілки в next (`умова>id\|...`), yes/no тоді порожні |
| `and` | паралельний шлюз: розгалуження (`next=4\|5`) або злиття (кілька елементів ведуть у нього) |
| `timer` | очікування часу / настання дати |
| `msg` | очікування повідомлення |
| `sub` | згорнутий підпроцес, описаний окремо |
| `linkStart` / `linkEnd` | пара подій-посилань для розриву довгого потоку; ОБОВ'ЯЗКОВО однаковий label в обох |
| `note` | текстова анотація — важлива примітка до кроку |
| `data` | документ / об'єкт даних, який створюється чи використовується кроком |
| `db` | ІТ-система / база даних, задіяна у кроці |

## Змістовні правила

1. **Нічого не вигадуй.** Якщо в описі бракує інформації (хто виконує крок, куди веде гілка, термін) — став у label позначку `[TO DEFINE: що саме невідомо]`. Якщо опис суперечить сам собі — теж `[TO DEFINE: суть суперечності]`.
2. **Полярність шлюзів.** Перевір двічі: гілка `yes` веде туди, куди процес іде при відповіді «Так» на питання в label.
3. **Ролі пиши консистентно** — та сама роль завжди однією й тією ж назвою (вона стане доріжкою на діаграмі). Ролей зазвичай 2–5.
4. **Кожен елемент потоку досяжний:** до нього веде хоч один next/yes/no (крім start), і він кудись веде (крім end).
5. **Петлі дозволені й потрібні:** повернення на доопрацювання — це `no` шлюзу або next задачі, що вказує на ранній id.
6. **Рівень деталізації:** один рядок = одна дія одного виконавця. Не дроби на мікрокроки («відкрити Jira», «натиснути кнопку») і не склеюй різних виконавців у один крок.
7. **Умовні/необов'язкові дії** («за потреби», «якщо необхідно») — або шлюз xor, якщо це значуща розвилка, або анотація note до кроку, якщо це нюанс виконання.
8. **Системні вимоги, які не є кроками потоку** («має бути можливість X») — в анотацію, не в потік.

## Приклад

Опис: «Співробітник подає заявку на доступ. Система перевіряє заповненість полів — якщо чогось бракує, повертає на доповнення. Далі керівник погоджує або відхиляє з коментарем. Погоджені заявки виконує адміністратор. SLA погодження — 2 робочі дні.»

```
id,label,type,role,next,yes,no,assoc
1,Виникла потреба в доступі,start,,2,,,
2,Подати заявку на доступ,task,Співробітник,3,,,
3,Перевірити заповненість полів,srv,Система,4,,,
4,Поля заповнені?,xor,,,6,5,
5,Доповнити заявку,task,Співробітник,3,,,
6,Розглянути заявку,task,Керівник,7,,,
7,Заявку погоджено?,xor,,,9,8,
8,Відхилити з коментарем,task,Керівник,10,,,
9,Надати доступ,task,Адміністратор,11,,,
10,Заявку відхилено,end,,,,,
11,Доступ надано,end,,,,,
n1,SLA погодження — 2 робочі дні,note,,,,,6
```

## Після генерації — самоперевірка

Перед видачею перевір по черзі: (1) заголовок точно `id,label,type,role,next,yes,no,assoc`; (2) жодної коми в label; (3) кожен type — зі словника; (4) всі id у next/yes/no/assoc існують; (5) полярність кожного шлюзу; (6) роль у кожної задачі; (7) прогалини позначені [TO DEFINE], а не заповнені здогадками.
